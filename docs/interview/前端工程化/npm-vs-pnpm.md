# npm 和 pnpm 的具体实现原理

## npm 

### 扁平化依赖 (npm v3+)

npm v3 之前使用嵌套结构，导致路径过长和重复依赖。v3 开始采用扁平化结构，将依赖提升到 `node_modules` 顶层。

**问题：**

1. **幽灵依赖 (Phantom Dependencies)**: 项目可以直接访问未在 `package.json` 中声明但被 hoisted 的依赖。
2. **依赖分身 (Doppelgangers)**: 不同版本的同一依赖可能被多次安装。

## pnpm 

### 内容寻址存储 (Content-addressable store)

pnpm 使用硬链接 (Hard links) 和符号链接 (Symbolic links) 来管理依赖。

1. **全局存储**: 所有依赖都存储在全局的 store 中 (`~/.pnpm-store`).
2. **硬链接**: 项目的 `node_modules` 下的 `.pnpm` 目录包含指向全局 store 的硬链接。
3. **符号链接**: 项目的 `node_modules` 根目录下的包是指向 `.pnpm` 目录中对应包的符号链接。

### 优势

1. **节约磁盘空间**: 同一版本的依赖只存储一次。
2. **安装速度快**: 大量复用缓存。
3. **严格的依赖管理**: 避免了幽灵依赖，只能访问 `package.json` 中声明的依赖。

# 硬链接 vs 软链接

简单来说：**硬链接是“备份/分身”，软链接是“快捷方式”。**

## 核心概念：Inode (索引节点)

### 前置知识：文件到底是什么？

在 Linux/Unix 系统中，一个文件由两部分组成：

1. **用户数据 (Data)**：文件的实际内容（存在磁盘块上）。
2. **元数据 (Metadata)**：文件的属性（大小、权限、创建时间等）和 **数据的地址**。这部分信息存在 **Inode** 中。

**文件名** 其实只是一个“指针”，它指向了这个 Inode。

### 硬链接 (Hard Link)

**定义**：
硬链接就是在同一个文件系统中，**给同一个 Inode 分配了多个文件名**。

**技术特点**：

- **共享 Inode**：源文件和硬链接文件拥有**相同的 Inode 号**。
- **地位平等**：它们互为硬链接，没有“原件”和“副本”之分。修改其中一个的内容，另一个也会变（因为改的是同一块数据）。
- **删除机制**：删除其中任何一个文件名，只是将 Inode 的“链接数”减 1。只有当链接数变为 0 时，系统才会回收磁盘空间。
- **限制**：
- 不能跨分区（文件系统）创建。
- 不能对目录创建硬链接（为了防止递归循环）。

**在 pnpm 中的应用**：
`pnpm` 把包下载到全局 Store，然后在你的项目里创建一个硬链接。

### 软链接 (Soft Link / Symbolic Link)

**定义**：
软链接（也叫符号链接）是一个**特殊的文件**，这个文件里存的内容是**另一个文件的路径**。

**形象比喻**：
Windows 桌面上的 **“快捷方式”**。

- 你有一个游戏安装在 `D:\Games\WoW.exe`。
- 你在桌面创建了一个快捷方式。
- 双击快捷方式，系统会根据路径去找那个 exe。
- 如果你把 `D:\Games\WoW.exe` 删了，桌面的快捷方式还在，但双击会报错（找不到文件）。

**技术特点**：

- **独立的 Inode**：软链接有自己的 Inode，和源文件不一样。
- **依赖性**：它依赖于源文件。如果源文件被删除或移动，软链接就变成了“死链接”（Dangling Link）。
- **灵活性**：
- 可以跨分区/文件系统。
- **可以对目录创建软链接**（这是它最强大的地方）。

**在 pnpm 中的应用**：
`pnpm` 利用软链接来构建 `node_modules` 的依赖树。

- 它把那些复杂的依赖关系（A 依赖 B），通过软链接一层层指引到正确的位置，解决了 Node.js 寻址的问题。

### 总结对比图

为了方便记忆，我整理了这个对比表：

| 特性           | 硬链接 (Hard Link)                        | 软链接 (Soft Link)                  |
| -------------- | ----------------------------------------- | ----------------------------------- |
| **本质**       | 同一个文件的不同名字 (同一个 Inode)       | 一个存着路径的新文件 (不同的 Inode) |
| **比喻**       | **备用钥匙**                              | **桌面快捷方式**                    |
| **删除源文件** | **无影响** (只要还有一个硬链在，数据就在) | **失效** (变成死链接)               |
| **跨文件系统** | 不可以                                    | **可以**                            |
| **目录链接**   | 不可以                                    | **可以**                            |
| **磁盘空间**   | 几乎为 0 (只占目录项)                     | 很小 (只存路径字符串)               |

### 实际演示 (命令行视角)

如果你在终端里输入 `ls -li` (显示 Inode)：

```bash
# 1. 创建一个文件 A
$ echo "Hello" > A.txt
$ ls -li A.txt
123456 -rw-r--r-- 1 user group 6 A.txt
# (注意：Inode 是 123456，链接数是 1)

# 2. 创建硬链接 B
$ ln A.txt B.txt
$ ls -li *.txt
123456 -rw-r--r-- 2 user group 6 A.txt
123456 -rw-r--r-- 2 user group 6 B.txt
# (注意：Inode 都是 123456，链接数变成了 2)

# 3. 创建软链接 C
$ ln -s A.txt C.txt
$ ls -li *.txt
123456 -rw-r--r-- 2 user group 6 A.txt
123456 -rw-r--r-- 2 user group 6 B.txt
789012 lrwxrwxrwx 1 user group 5 C.txt -> A.txt
# (注意：C 的 Inode 是 789012，它是全新的文件，且指向 A)

```

**一句话总结：**
**硬链接**用来**省空间**（多处使用同一份数据），**软链接**用来**指路**（跨目录构建逻辑关系）。这也是 `pnpm` 高效的核心秘密。

# 多人协作：如何让别人优先复用已有组件并统一代码风格

> 面试场景题：多人协作的项目里，怎么保证别人开发时尽量复用已经写好的 / 已经存在的组件，并且保持代码风格一致？
> 同题变体："团队里每个人各写各的组件怎么办？""怎么推进组件库落地？""AI 写代码越来越多之后，怎么保证 AI 也用你们的组件？"

## 核心观点（开场就说这句）

让别人优先复用组件，**不能靠口头提醒、会议强调和群公告**。真正起作用的是三件事：

> **组件好找、组件好用、乱写会被拦住。**

| 层次 | 目标 | 他为什么愿意用 |
| --- | --- | --- |
| **好找** | 10 秒内知道"有没有现成组件、该用哪个" | 不查文档比查文档还快，人就会自己写 |
| **好用** | 用你的组件比自己写更快、更省事 | 复用变成"占便宜"，而不是"被约束" |
| **拦住** | 绕过去自己写时，工具链当场报错 | 规范不靠自觉，靠流程兜底 |

只做到第一条，是"文档式规范"；三条都做到，才叫"工程化约束"。

## 一、让组件好找：统一沉淀 + 文档

### 1. 集中管理，物理隔离

```
src/
├── components/
│   ├── common/        # 通用组件：和业务无关，可跨项目复用（BaseTable、SearchForm）
│   └── business/      # 业务组件：绑定当前业务的领域概念（UserSelector、OrderStatusTag）
└── pages/             # 页面里只允许写业务编排，不允许写可复用 UI
```

- 通用组件和业务组件**分开存放**，避免"业务组件被当成通用组件到处引"，也避免通用组件里混进接口请求。
- Monorepo 场景下把通用组件抽成独立的 `packages/ui`，版本独立、可被多个应用消费；业务组件留在各自应用里。

### 2. 统一出口，路径不暴露

每个目录下放 `index.ts` 统一导出，使用时只认一个入口：

```ts
// src/components/index.ts
export * from "./common";
export * from "./business";
```

```ts
// 业务代码里：不用记具体路径，也方便以后整体迁移
import { BizTable, UserSelector } from "@/components";
```

好处：内部目录怎么重构，调用方都不用改；组件的"查找入口"只有一个，不会出现三处同名组件。

### 3. 可视化文档站

用 **Storybook**（React）/ **dumi、VitePress + 组件 demo 插件**（Vue）搭一个组件文档站，每个组件必须写清楚四件事：

1. **示例**：可交互的 Demo，直接能复制跑
2. **Props 说明**：表格化的 API，默认值、类型、说明
3. **使用场景**：什么业务下该用它（这一条最容易被省略，但最有用）
4. **注意事项**：不支持什么、有什么坑、和其他组件的区别

> 面试加分点：文档站要能把"业务场景"作为搜索入口。新人搜"上传"能找到 `BizUpload`，搜"表格"能找到 `ProTable`，而不是靠老员工口口相传。

### 4. 命名规范，让搜索能命中

- 前缀统一：`BaseXxx` 表示无业务的底座组件，`BizXxx` 表示业务组件，`ProXxx` 表示增强版。
- 命名语义化：`UserSelector` 比 `SelectUser`、`UserPick`、`ChooseUser` 都好搜。
- 禁止一个功能多个近义名，命名一旦定下就写进规范文档。

## 二、让组件好用：设计要考虑扩展

复用率低，很多时候不是别人不查，而是**组件改不动**，用起来别扭，只好自己重写一个。所以组件本身的设计要"抗造"。

### 1. Props 设计贴近 UI 库的习惯

不要让使用者重新学一套心智模型：底层是 antd / Element Plus，Props 命名、事件名、可选值风格就保持一致，降低迁移成本。

### 2. 留出扩展点，别把路堵死

必须支持：`className` / `style` 透传、剩余属性透传（`v-bind="$attrs"` / `...rest`）、默认插槽与具名插槽、作用域插槽、`render` 函数或组件插槽、`ref` 暴露方法（`defineExpose` / `useImperativeHandle`）。

```vue
<!-- Vue：透传 + 插槽 + 暴露方法，三种扩展点齐了 -->
<script setup lang="ts">
defineProps<{ title: string; loading?: boolean }>();
const open = () => { /* ... */ };
defineExpose({ open });
</script>

<template>
  <div class="biz-card" v-bind="$attrs">
    <header>{{ title }}<slot name="extra" /></header>
    <slot />
  </div>
</template>
```

### 3. 覆盖 80% 场景，剩余 20% 也能接住

组件只要满足大部分常见需求，同时给特殊需求留扩展口（插槽、`render`、`config` 字段），别人就不会因为有 10% 不满足而整个重写。

### 4. 类型完善

TypeScript 类型写全、**禁止 `any`**。IDE 自动补全和类型报错本身就是最好的使用文档，用起来成本低，复用意愿自然高。同时清晰的 `interface` 也是给 AI 检索用的（见第五节）。

### 5. 有 owner、持续维护

每个公共组件指定负责人。别人提需求（新增 Props、加插槽）能及时响应——**维护不跟上，别人就会自己另写一个**，这是组件库腐化的头号原因。

## 三、让乱写被拦住：工程化约束

规范靠自觉一定会退化，必须有工具链兜底。

| 手段 | 具体做法 | 效果 |
| --- | --- | --- |
| **ESLint 规则** | `no-restricted-imports` 禁止直接引入底层组件（如直接用 antd 的 `Modal`、`Table`） | 写代码时当场报错 |
| **Code Review** | PR 模板增加"是否复用已有组件"检查项 | 人工兜底，覆盖工具管不到的场景 |
| **Git Hooks** | husky + lint-staged 提交前校验 | 不合规的代码提交不上去 |
| **代码片段** | VS Code snippets / AI 编码规则文件 | 默认就生成规范代码，而不是错误代码 |
| **组件库出 P0 缺陷走流程** | 发现问题改组件，不允许页面里打补丁 | 防止"每页各修一遍" |

### ESLint 拦截示例（ESLint 9 flat config）

```js
// eslint.config.js
export default [
  {
    rules: {
      "no-restricted-imports": [
        "error",
        {
          paths: [
            {
              name: "antd",
              importNames: ["Modal", "Table", "Upload"],
              message: "请勿直接使用 antd 的 Modal/Table/Upload，请改用 @/components 下的 BizModal、ProTable、BizUpload。",
            },
          ],
          patterns: [
            {
              group: ["**/components/common/*"],
              message: "请从 @/components 统一入口引入，不要直接引用内部路径。",
            },
          ],
        },
      ],
    },
  },
];
```

关键在 **message 要写清楚"该换成什么、从哪导入"**：报错信息本身就是一份即时文档，新人看到就知道去哪找。

### 提交卡点

```json
// package.json
{
  "lint-staged": {
    "*.{ts,tsx,vue,js}": ["eslint --fix", "prettier --write"]
  }
}
```

配合 husky 的 `pre-commit` 钩子，不合规代码根本进不了仓库。

## 四、团队协作机制（工具之外的那一半）

- **新人引导**：入职文档写明"开发前先查组件库"，附组件清单和使用规范的链接，入职第一周就建立习惯。
- **新增流程**：确实需要新组件时，先在群里 / 评审中确认没有可复用的，再决定是**扩展旧组件**还是**新建**，并登记到组件清单。避免"一个新需求产生一个新组件"。
- **变更同步**：组件更新写 CHANGELOG，破坏性变更按语义化版本（SemVer）管理并通知使用方，避免悄悄改坏别人的页面。
- **定期治理**：定期扫描重复实现（相似度扫描 / 人工盘点），把功能重叠的组件合并沉淀到公共库。组件库是**要持续减肥的**。

> 一句话总结机制部分：**入口统一、新增有门槛、变更可追溯、定期做合并。**

## 五、AI 时代：怎么让 AI 也优先复用已有组件

现在大量代码是 AI 写的，"别人"很多时候就是同事 IDE 里的 AI。传统约束依然有效，但要多做三件事。

### 1. 把 AI 规则纳入 Git 版本控制

主流工具都支持项目级规则文件：`.cursor/rules/*.mdc`、`CLAUDE.md`、`.github/copilot-instructions.md`、`AGENTS.md`。**提交到仓库**，全员拉下来后共享同一套约束。

两件事必须写进去：

- **强指令约束（红线）**：明确禁止直接使用底层组件，指明替代品。例如"禁止直接使用 antd 的 `Modal`、`Table`，必须优先从 `@/components` 引入 `BizModal`、`ProTable`"。
- **组件索引表（Component Registry）**：维护一份极简的 `components-map.md`，每个私有组件一两句话说明用途和路径，让 AI 精准检索而不是盲扫全盘代码。

```md
<!-- components-map.md -->
- UserSelector (@/components/UserSelector): 选择公司员工 / 部门，支持多选与部门级联。选人场景一律用它，不要用裸 Select 拉接口。
- ProTable (@/components/ProTable): 带查询表单、分页、列配置的服务端表格。列表页一律用它。
- BizUpload (@/components/BizUpload): 上传到阿里云 OSS，内置签名、进度、大文件分片。
```

### 2. 写"AI 友好型"的组件（元信息即检索素材）

以前注释是给人看的，现在 JSDoc 和 TS 类型是给 AI 做**代码库索引 / RAG 向量检索**用的：

- **语义化 JSDoc**：在组件头部写清 `@description` 和适用场景。例如"当表单需要上传文件到阿里云 OSS 时使用"，AI 在被要求写上传功能时命中率会明显提升。
- **严禁 `any`，导出清晰 Props 类型**：AI 读了 `interface` 才能一次生成符合规范的传参代码，而不是自己编属性。

```ts
/**
 * 业务卡片容器
 * @description 后台管理列表页 / 详情页的白色卡片容器，统一内边距与标题样式。
 * 适用场景：需要"标题 + 右上角操作 + 内容区"的页面区块。
 * 不建议用于：弹窗内部内容（请用 BizModal 自带的内容区）。
 */
export interface BizCardProps {
  /** 卡片标题 */
  title: string;
  /** 右上角操作区，通常放按钮 */
  extra?: React.ReactNode;
}
```

### 3. 进阶：组件库 MCP Server 或 `llms.txt`

如果组件库独立成包 / 跨仓库，本地 AI 扫不到源码，就要把知识外置：

- **生成 `llms.txt`**：在组件文档站构建时用脚本把所有组件的签名、简短说明、一句话 Demo 打成纯文本，作为外部知识源喂给 AI。
- **配置 MCP Server**：给内部组件库写一个轻量 MCP Server。同事在 IDE 里让 AI 写页面时，AI 会主动调用工具查询"当前团队有哪些现成组件？ProTable 的最新 API 是什么？"，拿到最准确的私有组件上下文。

### 4. 形成"AI 自我修复"闭环

AI 也会幻觉或不听话，所以传统卡点在 AI 时代变成了**给 AI 的实时反馈机制**：

在 Cursor Agent / Claude Code 这类 agent 模式下，如果 AI 错误引用了原生 `el-upload`，终端或 IDE 的 Problems 面板会立刻抛出定制的 ESLint 报错：

```
❌ 请勿直接使用 el-upload，请改用 @/components/BizUpload
```

AI 读到这条报错后，往往几秒内就自动改成团队的私有组件，**不需要人工干预**。这就是"既统一风格、又不打断开发心流"的关键：约束的反馈回路越短，规范越容易被遵守（人和 AI 都一样）。

## 六、面试口述版

### 60 秒版（先给结论）

> 我会从三个方向做：**好找、好用、好拦**。
> 第一，组件集中沉淀，用 `index.ts` 统一出口、Storybook 或 dumi 出文档，写明示例、Props 和使用场景，命名统一成 `BaseXxx` / `BizXxx`，让人搜得到。
> 第二，组件本身要好用——Props 贴近 UI 库习惯、支持透传和插槽、类型写全、有 owner 维护。复用率低很多时候不是别人不查，而是组件改不动。
> 第三，上工程化约束：用 ESLint 的 `no-restricted-imports` 禁止直接引底层组件，报错信息里写明该换成哪个组件；PR 模板加复用检查项；husky + lint-staged 做提交卡点。
> 最后配套机制：新人引导、新增组件要评审、变更走 CHANGELOG 和语义化版本、定期合并重复组件。

### 3 分钟版（加 AI 时代那一段）

> 在 AI 大量参与编码之后，我会把重点放到"让 AI 也复用"上，具体三步：
>
> **第一，把 AI 规则纳入 Git 版本控制。** 在项目根目录维护 `.cursor/rules` 或 `CLAUDE.md`，在里面写死组件调用红线，并维护一份轻量的私有组件索引表（`components-map.md`），让全团队的 AI 都知道遇到什么业务场景该去哪个路径找现成组件。
>
> **第二，写"AI 友好型"的组件代码。** 要求公共组件必须有语义清晰的 JSDoc 场景描述和严格的 TS 类型，这能极大提升 AI 对本地代码库做向量检索时的命中率，也让它不会瞎编 Props。
>
> **第三，用 ESLint 构建 AI 自动纠错闭环。** 通过 `no-restricted-imports` 拦截原生底层组件，并在报错信息里写明替换组件的导入路径。这样 AI 在 Agent 模式下写错时，读到 Linter 报错就能自己瞬间改用业务组件——既统一了代码风格，又不打断开发心流。
>
> 如果组件库是跨仓库的独立包，我还会在文档站构建时产出 `llms.txt`，或者直接给组件库写一个 MCP Server，让 AI 主动查"我们有哪些现成组件"。

## 七、面试官常见追问

**Q1：为什么不直接靠 Code Review 和规范文档？**
A：CR 是最后一道人工兜底，成本高、有延迟、有情绪摩擦，而且拦不住 AI 批量产出的代码。规范文档的转化率很低。工具链的反馈是**即时、零成本、无争议**的，能自动化的就别靠人。

**Q2：组件被滥用扩展点怎么办（比如到处传 `style` 把样式改乱）？**
A：扩展点要"有边界"。视觉层统一走主题变量 / design token，不鼓励在业务里传裸 `style`；确实需要的差异用 `variant`、`size` 这类语义化 Props 收敛，而不是开放任意样式。同时用 Stylelint 约束样式写法。

**Q3：怎么衡量组件复用做得好不好？**
A：几个可观测指标——公共组件的引用次数与覆盖率、新增组件数量（应该趋于收敛而不是线性增长）、重复实现的相似度扫描结果、以及"页面里直接引用 UI 库底层组件"的 ESLint 告警数量。指标下降就是治理有效。

**Q4：组件库改了会不会把别人项目搞坏？**
A：独立包用语义化版本 + CHANGELOG，破坏性变更走 major 并提前通知；应用内组件改动必须过 CI；关键组件有单测和视觉回归（Storybook + Chromatic 之类），防止改 A 坏 B。

**Q5：新人和老人习惯难改怎么办？**
A：不指望一次说服。做法是让"正确路径更省事"：脚手架模板 / 代码片段 / AI 规则文件默认生成的就是规范代码，再配合前置的 ESLint 报错。当走正确路径比走错误路径更省时间时，习惯自然就迁移了。

## 八、附录：可直接使用的模板

### 1. `.cursor/rules/components.mdc`（组件与风格约束）

```md
---
description: 组件复用与代码风格红线
globs: ["src/**/*.{ts,tsx,vue}"]
alwaysApply: true
---

# 组件复用红线（必须遵守）

1. 禁止直接从 UI 库引入以下组件，必须使用团队封装版本：
   - antd `Modal` → `@/components/BizModal`
   - antd `Table` → `@/components/ProTable`
   - antd `Upload` → `@/components/BizUpload`
   - Element Plus `el-upload` → `@/components/BizUpload`
2. 所有组件一律从 `@/components` 统一入口引入，禁止引用 `@/components/common/*` 等内部路径。
3. 写任何列表页、表单页、弹窗之前，先阅读 `.ai/components-map.md`，确认是否已有现成组件。
4. 找不到合适组件时，不要自己新建，先在回答里说明"现有组件 X 不满足需求，建议扩展 Y"，等确认后再写。

# 代码风格

- TypeScript 严格模式，禁止 `any`；组件 Props 必须显式导出 interface。
- Vue 一律 `<script setup lang="ts">`；React 一律函数组件 + Hooks。
- 样式使用 `<style scoped>` / CSS Modules，颜色、间距必须使用主题变量，禁止硬编码色值。
- 私有函数必须写明用途；导出组件必须写 JSDoc，包含适用场景。
```

### 2. `.ai/components-map.md`（组件索引表）

```md
# 组件索引
> 用途：给人和 AI 检索用。新增组件必须在此登记。

## 通用（@/components/common）
- BaseButton (@/components/common/BaseButton): 统一按钮，支持 type/size/loading/防抖提交。
- ProTable (@/components/common/ProTable): 服务端分页表格，内置查询表单、列配置、导出。列表页首选。
- BizModal (@/components/common/BizModal): 弹窗封装，统一宽度/滚动/关闭确认。禁止直接用 antd Modal。

## 业务（@/components/business）
- UserSelector (@/components/business/UserSelector): 选择员工/部门，支持多选与部门级联。选人场景一律使用。
- OrderStatusTag (@/components/business/OrderStatusTag): 订单状态标签，内置颜色与文案映射，禁止在页面里手写 if-else 映射。
```

### 3. PR 模板检查项

```md
## 自查清单
- [ ] 已查阅组件索引，本次改动复用了已有组件（如无，请说明原因）
- [ ] 未直接引用 UI 库底层组件（Modal / Table / Upload 等）
- [ ] 新增组件已登记到 components-map.md，并补充了 Storybook 示例与 JSDoc
- [ ] 未新增硬编码颜色 / 间距，样式使用主题变量
- [ ] 本地 `pnpm lint` 通过
```

### 4. 一句话收尾

> 组件复用不是"让人自觉"，而是**把复用的成本降到比自研更低，把绕过的成本抬到比复用更高**。

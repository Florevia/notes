## Vite 为什么快？

Vite 之所以快，核心在于它利用了 **浏览器原生的 ESM 能力** ，并采用了 **No-Bundle（不打包）** 的开发模式，将繁重的构建工作交给了 **浏览器和高性能工具（esbuild）**。
具体原理可以分为以下三个维度来阐述：

1. **开发环境：基于原生 ESM 的按需编译（核心原理）**
   - 传统的构建工具（如 Webpack）在启动开发服务器前，必须先解析整个依赖图，将所有模块打包成 Bundle，然后才能启动服务。项目越大，启动越慢。

   - Vite 采取了不同的策略：
     - 利用浏览器原生能力：现代浏览器支持 `<script type="module">`。Vite 直接向浏览器提供源码。

     - 按需编译：当浏览器解析到 import 请求时，Vite 开发服务器拦截该请求，仅对该模块进行必要的编译（如 TS 转 JS、Sass 转 CSS）并返回。

   - 结果：启动时间与项目复杂度解耦，几乎是秒开。

2. **依赖预构建：利用 esbuild 的高性能**
   - Vite 将代码分为“源码”和“依赖”两部分。

   - 源码：是我们写的业务代码，变动频繁，通过原生 ESM 加载。

   - 依赖：是 **node_modules** 中的库，变动极少。Vite 使用 esbuild 对其进行预构建。
     - 速度快：esbuild 使用 Go 编写，比基于 Node.js 的打包工具（如 Webpack/Rollup）快 10-100 倍。

     - 格式统一：将 CommonJS/UMD 转换为 ESM。

     - 性能优化：将许多内部模块（如 lodash-es）合并成一个文件，避免浏览器发起成百上千个 HTTP 请求（解决 HTTP 瀑布流问题）。

3. **热更新（HMR）：O(1) 复杂度**
   - Webpack HMR：修改文件后，通常需要重新构建模块及其依赖图的一部分，随着应用规模增长，热更新速度会下降。

   - Vite HMR：利用 ESM，当某个模块修改时，Vite 只需要让浏览器重新请求该特定模块即可。无论项目多大，热更新速度始终保持在一个极低的常量时间（O(1)）。

4. **强缓存策略**
   - 依赖模块：设置了 **强缓存（Cache-Control: max-age=31536000, immutable）**，一旦预构建完成，除非锁文件变动，否则直接走浏览器缓存。

   - 源码模块：使用 **304 协商缓存**，进一步减少网络开销。

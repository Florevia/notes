# 单元测试

## 概念

**单元测试（Unit Testing）** 是对软件中 **最小可测试单元** 进行检查和验证的过程。

在前端开发中，它通常是一个 **纯函数**、一个 **组件** 或者一个 **Hook**。

## 核心原则

1. **隔离性 (Isolated)**:

这是最重要的特点。测试目标代码时，必须与外部环境切断联系（Mock 掉 API 请求、数据库、全局 Store、浏览器 DOM 等）。只测逻辑，不测依赖。

2. **原子性 (Atomic)**:

一个测试只测一个具体的功能点或分支。

3. **快速 (Fast)**:

单个测试运行时间通常在毫秒级。几千个测试应该在几分钟内跑完。如果跑得慢，开发者就不会愿意频繁运行它。

4. **自动化 (Automated)**:

不需要人工干预，通过命令行（CLI）或 CI/CD 流水线自动触发

## 解决问题

### 回归测试

- 痛点： 你修复了一个 Bug，结果导致另一个 unrelated 的功能挂了。

- 解决： 每次代码提交前，自动运行几千个测试用例。如果新代码破坏了旧逻辑，测试会立马变红报错。

### 重构信心

- 痛点： 面对复杂的遗留代码，虽然写得很烂，但因为它能跑，没人敢优化。

- 解决： 如果有高覆盖率的单测，你可以大胆重构。只要改完后测试依然通过（Green），就说明你的重构是安全的。

### 活体文档

- 痛点： 需求文档由 PM 写，经常过时；注释可能是两年前的。

- 解决： 测试用例是永远同步的文档。看一眼 it('should return error when input is empty')，就知道这个函数原本设计是用来干嘛的。

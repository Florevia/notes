# CI/CD 企业级实践 (面试回答整理)

它是一套通过 **自动化脚本** 来串联 **代码提交** 到 **应用上线** 全过程的机制。

## 1. 什么是 CI/CD？

它包含三个概念，层层递进：

### CI (Continuous Integration - 持续集成)

- **核心动作**：开发人员频繁地（每天多次）将代码合并到主干。
- **自动化流程**：`代码提交` → `自动触发构建` → `运行单元测试/静态检查`。
- **目的**：“提早发现问题”（Fail Fast），解决代码冲突。

### CD (Continuous Delivery - 持续交付)

- **核心动作**：在 CI 通过后，自动化将代码部署到 **“类生产环境”（预发环境）**。
- **状态**：软件随时处于 **“可由人工点击部署到生产环境”** 的状态。
- **目的**：确保软件质量可靠，降低发布风险。

### CD (Continuous Deployment - 持续部署)

- **核心动作**：持续交付的下一步。如果没有人工审核环节，所有通过自动化测试的代码都会**自动发布**到生产环境。
- **目的**：极致的交付速度（常见于互联网大厂的核心业务）。

## 2. 在企业中是如何实践的？

在实际工作中，CI/CD 通常由 **GitLab CI**、**Jenkins** 或 **GitHub Actions** 等工具驱动。

### 第一阶段：本地开发与提交 (Pre-commit)

在代码进入 CI 管道之前，先在本地进行质量控制。

- **工具**：`Husky` + `Lint-staged` + `commitlint`
- **动作**：`git commit` 时触发钩子，强制执行 ESLint/StyleLint 和 Commit 规范检查。不合格的代码根本推不上去。

### 第二阶段：CI 流水线 (Pipeline - Build & Test)

当代码 push 到 GitLab/GitHub 后，触发 CI 脚本：

1. **Install**：拉取依赖 (`npm ci` 或 `pnpm install --frozen-lockfile`，确保版本一致)。
2. **Lint & Test**：全局运行 Lint 检查，跑单元测试 (`Jest`/`Vitest`)。如果失败，流水线红灯，并发送邮件/钉钉通知给对应开发者。
3. **Build**：执行构建 (`npm run build`)。
   - **前端产物**：生成 HTML/CSS/JS 静态资源。
4. **容器化（可选）**：构建 Docker 镜像，并打上 tag（通常是 commit hash 或时间戳）。

### 第三阶段：制品管理 (Artifacts)

- **非容器化**：将 build 生成的 `dist` 目录压缩，上传到制品库（如 Nexus）或直接上传到对象存储（AWS S3 / 阿里云 OSS）。
- **容器化**：`docker push` 镜像到私有镜像仓库（Harbor）。

### 第四阶段：CD 流水线 (Deploy)

这一步通常分为多个环境，通过分支或 Tag 触发：

- **开发/测试环境 (Dev/QA)**：只要 `dev` 分支有更新，立即自动部署。
- **预发布环境 (Staging/UAT)**：环境配置与线上几乎一致，用于回归测试。
- **生产环境 (Production)**：通常需要 **Tech Lead 点击“确认部署”按钮 (Approval)**，随后上传资源到 CDN 并刷新缓存。

## 3. 企业级实践中的关键策略

在高级的实践中，为了保证高可用，我们通常还会配合以下策略：

- **灰度发布（金丝雀发布 Canary）**

  不一次性替换所有服务。先切 10% 的流量到新版本，观察 **Sentry** (错误监控) 和业务数据。如果没有报警，再逐步扩大到 100%。

- **蓝绿部署 (Blue-Green)**

  准备两套环境。新版本部署在“绿”环境，测试通过后，并在网关层（Nginx/Ingress）**瞬间切换流量**指向“绿”环境。如果出问题，瞬间切回“蓝”环境。

- **版本回滚 (Rollback)**

  CI/CD 系统必须支持“一键回滚”。因为镜像或静态资源包都是按版本号归档的，回滚其实就是重新部署上一个版本的镜像。

---

## 总结

对前端来说，CI/CD 强制了代码规范，保证了测试覆盖，并且让上线过程变得 **可追溯、可回滚**，是保障工程质量的底线。

# 垃圾回收和内存泄漏

## 1. 垃圾回收 (Garbage Collection)

### 1.1 什么是垃圾回收？

垃圾回收是一种自动内存管理机制，用于查找并释放不再使用的内存。js 使用自动垃圾回收，开发者无需手动释放内存。

### 1.2 垃圾回收算法

#### 1.2.1 引用计数（Reference Counting）

**原理：** 跟踪每个值被引用的次数，当引用次数为 0 时回收。

```js
let obj1 = { name: "Alice" }; // 引用计数: 1
let obj2 = obj1; // 引用计数: 2
obj1 = null; // 引用计数: 1
obj2 = null; // 引用计数: 0，可回收
```

**缺点：** 无法处理循环引用

```js
function problem() {
  let obj1 = {};
  let obj2 = {};
  obj1.ref = obj2; // 互相引用
  obj2.ref = obj1;
  // 函数结束后，引用计数仍不为 0，无法回收
}
```

#### 1.2.2 标记清除（Mark-Sweep）- 主流算法

**原理：**

1. 从根对象（全局对象、当前执行上下文）开始遍历
2. 标记所有可访问的对象
3. 清除未被标记的对象

```js
function noProblem() {
  let obj1 = {};
  let obj2 = {};
  obj1.ref = obj2;
  obj2.ref = obj1;
}

noProblem();
// 函数结束后，obj1 和 obj2 不可访问，会被回收
// ✅ 解决了循环引用问题
```

#### 1.2.3 V8 的优化 - 分代回收

**新生代：**

- 存放生存时间短的对象
- 使用 Scavenge 算法（复制算法）
- 内存分为 From 空间和 To 空间
- 回收频率高，速度快

**老生代：**

- 存放生存时间长的对象
- 使用标记清除 + 标记整理
- 回收频率低

**晋升机制：**

- 经过一次 Scavenge 仍存活 → 晋升到老生代
- To 空间使用率 > 25% → 直接晋升

#### 1.2.4 增量标记（Incremental Marking）

为了避免长时间阻塞 JavaScript 执行，将标记过程拆分成多个小步骤，与 JS 执行交替进行：

```
JS执行 → GC标记 → JS执行 → GC标记 → JS执行 → GC清除
```

配合技术：

- 懒清除（Lazy Sweeping）
- 并发标记（Concurrent Marking）
- 并行清除（Parallel Sweeping）

## 2. 内存泄漏 (Memory Leak)

### 2.1 什么是内存泄漏？

内存泄漏是指不再使用的内存没有被及时释放，导致内存占用持续增长，严重时会导致程序崩溃。

### 2.2 常见内存泄漏场景

#### 2.2.1 意外的全局变量

```js
function foo() {
  bar = "global variable"; // ❌ 意外创建全局变量
  this.name = "global name"; // ❌ this 指向全局对象
}

foo();

// 解决方案：使用严格模式 ✅ （let/const）
```

#### 2.2.2 未清理的定时器

```js
// ❌ 内存泄漏
let data = new Array(1000000);

setInterval(() => {
  let node = document.getElementById("node");
  if (node) {
    node.innerHTML = JSON.stringify(data);
  }
}, 1000);
// 即使 node 被移除，定时器仍在运行，data 无法回收
```

#### 2.2.3 闭包导致的内存泄漏

```js
// ❌ 内存泄漏
function createClosure() {
  let largeData = new Array(1000000).fill("data");

  return function () {
    console.log(largeData[0]);
  };
}

let closure = createClosure();
// closure 持有 largeData 的引用，无法回收

// 解决方案：✅ 使用完毕后解除引用
closure = null;
```

#### 2.2.4 DOM 引用未清理

```js
// ❌ 内存泄漏
let elements = {
  button: document.getElementById("button"),
};

document.body.removeChild(document.getElementById("button"));
// button 已从 DOM 树移除，但 elements.button 仍持有引用

// 解决方案：✅ 清理引用
elements.button = null;
```

#### 2.2.5 事件监听器未移除

```js
// ❌ 内存泄漏
let element = document.getElementById("button");

element.addEventListener("click", function onClick() {
  console.log("clicked");
});

document.body.removeChild(element);
// 元素被移除，但监听器仍存在

// 解决方案：✅ 移除监听器
element.removeEventListener("click", onClick);
document.body.removeChild(element);
element = null;
```

#### 2.2.6 console.log

```js
// ❌ 可能导致内存泄漏
let largeObject = new Array(1000000);
console.log(largeObject);
// 某些浏览器的控制台会持有对象引用

// 解决方案：生产环境移除 console.log
```

### 2.3 检测内存泄漏

**Chrome DevTools - Memory：**

- **Heap Snapshot**：对比不同时间点的内存快照

- 步骤：

  - 分别在操作前后拍两张“堆快照”。

  - 对比（Comparison）这两张快照。

  - 搜索 "Detached"（脱离），查看有没有“Detached DOM tree”。这通常是 DOM 泄漏的铁证。

**Performance Monitor：**

- 实时监控 JS Heap Size

- 步骤：

  - 勾选 Memory。

  - 录制一段时间的操作。

  - 如果看到内存曲线呈现 **“锯齿状上升”**（不断涨，GC 后掉下来一点，但总体趋势是越来越高），说明有泄漏。

## 面试回答总结

**内存泄漏：**

1. 内存泄漏是指 **不再使用的内存没有被释放**。

常见场景包括：
- 意外的全局变量
- 未清理的定时器和事件监听器
- 闭包导致的引用无法释放
- DOM 引用未清理等
> 预防关键是及时解除引用、清理定时器和监听器、合理使用闭包，可以使用 **WeakMap/WeakSet** 等弱引用结构。
> 
> 开发中使用 **Chrome DevTools 的 Memory 面板** 检测和定位问题。


1. JS 引擎如何做内存管理和垃圾回收？

现代 JS 引擎（如 V8）主要将内存划分为栈空间（存储基础数据类型和引用地址）和堆空间（存储复杂对象）。它的垃圾回收（GC）基于分代收集理论：

新生代： 存放存活时间短的对象。采用 Scavenge 算法，将内存平分为 From 和 To 两部分。回收时将 From 中存活的对象复制到 To 中，然后清空 From，两者角色互换。回收频率高，速度快。

老生代： 存放经过多次新生代回收依然存活的对象，或体积过大的对象。采用 **标记-清除算法，遍历所有根对象标记存活节点，然后清除未标记的内存。回收频率低，速度慢。**

# 执行栈和执行上下文

> 彻底理解 **执行上下文** 和 **执行栈**，是掌握 **闭包**、**作用域链**、**变量提升** 以及 **this 指向** 的基础。

简单来说：

- **执行上下文** 是代码被 **解析** 和 **执行** 的环境。

- **执行栈** 是管理这些环境的容器。

## 执行栈

### 概念

- JS 是单线程语言，这意味着它同一时间只能做一件事。

- 为了管理代码的执行顺序，JS 引擎使用了一个 **后进先出（LIFO）** 的栈结构

- 这就是执行栈（也叫调用栈 Call Stack）。

### 工作流程

1. **初始化**： 当 JS 引擎开始读取脚本时，首先会创建一个 **全局执行上下文**，并将其推入栈底（这个全局上下文直到 **浏览器关闭** 或 **标签页关闭** 才会被弹出）。

2. **函数调用**： 每当引擎发现一个 **函数调用** 时，它会为该函数创建一个新的 **函数执行上下文**，并将其推入栈顶。

3. **执行**： 引擎始终执行栈顶的 **上下文**。

4. **弹出**： 当函数执行完毕，该上下文从栈顶弹出，控制权交还给下一个上下文。

## 执行上下文

### 概念

> 执行上下文就是当前 JS 代码被 **解析** 和 **执行** 时所在环境的抽象概念。

### 分类

1. **全局执行上下文 (Global EC)**： 默认的、最基础的上下文。

   - 任何不在函数内部的代码都在这里。

   - 它会创建全局对象（浏览器是 window，Node 是 global），并将 this 指向这个全局对象。

   - 一个程序中只有一个 全局 EC。

2. **函数执行上下文 (Function EC)**： 每次调用函数时，都会创建一个新的上下文。

   - 每个函数都有自己的上下文，但只有在被调用时才会被创建。

3. **Eval 执行上下文**： 运行在 eval() 函数中的代码（由于性能和安全原因，现代开发极少使用）。

### 执行上下文的生命周期（核心机制 🌟）

> 一个执行上下文的生命周期分为两个阶段：**创建阶段** 和 **执行阶段**。

#### 第一阶段：**创建阶段**

> 在代码真正执行之前，JS 引擎会扫描代码，进行 **预编译**。这个阶段决定了 **变量提升** 的行为。

**在这个阶段，引擎会做三件事（生成三个重要属性）：**

1.  确定 **this 的指向** (This Binding)：

    - 在全局环境下，指向 window。

    - 在函数环境下，取决于函数是如何被调用的。

2.  创建**词法环境** (Lexical Environment) / **作用域链** (Scope Chain)：

    - 确定当前环境能访问哪些变量，以及父级环境是谁。

    - 父级环境由函数 **声明的位置** 决定，而不是 **调用的位置**。

    ```js
    var a = 100;

    function dad() {
      var a = 200;

      // son 是在 dad 里面声明的
      // 所以 son 的父级环境就是 dad
      function son() {
        console.log(a);
      }

      return son;
    }

    var anotherCousin = dad(); // 执行 dad，拿到 son

    // 哪怕在这里调用，son 依然记得它的爸爸是 dad，而不是全局
    anotherCousin(); // 输出 200
    ```

3.  创建**变量对象** (Variable Object - VO)：

    - 这是 **变量提升发生的根本原因**。引擎会按照以下顺序填充 VO：

    - 函数参数 (Arguments)： 创建 arguments 对象，检查参数。

    - 函数声明 (Function Declaration)： 扫描 `function foo(){}`。如果名字已存在，完全覆盖。

    - 如果不巧出现了 **同名的标识符**，**函数声明** 有最高的“优先权”和“霸道权”：

      - 它可以覆盖掉同名的 **函数参数**。

      - 它可以覆盖掉同名的 **之前的函数声明**。

      ```js
      // 在创建阶段，引擎扫描到第二个 foo 时，会直接覆盖掉第一个 foo

      // 所以代码还没运行，foo 就已经是打印 2 的那个函数了

      function foo() {
        console.log(1);
      }

      function foo() {
        console.log(2);
      }

      foo(); // 输出 2
      ```

      经典案例：

      ```js
      console.log(a); // 输出：function a() {}

      // (证明：函数声明提升 覆盖了 变量提升，或者说变量声明被忽略了)
      var a = 10;
      function a() {}
      console.log(a); // 输出：10
      // (执行阶段：var a = 10 执行赋值，把 a 变成了数字)
      ```

- 变量声明 (Variable Declaration)： 扫描 `var a`。如果名字已存在，跳过（为了防止覆盖掉同名的函数声明）。注意：此时变量的值是 undefined。

#### 第二阶段：**执行阶段**

代码真正一行行运行的阶段。

- 在这个阶段，JS 引擎会完成 **变量赋值**、**函数引用** 以及 **执行其他代码**。

- 如果变量在创建阶段是 `undefined`，到了这一行才会被赋值为真实的值。

## 实战解析

```js
var a = 10;

function foo(i) {
  var b = 20;
  var c = function () {}; // 函数表达式
  function d() {} // 函数声明
  console.log(a + b + i);
}

foo(30);
```

### Step 1: 全局 EC 创建阶段

1. 栈底压入 **GlobalContext**。
2. **VO 扫描**：
   - 找到 `foo` 函数声明 -> 存入内存。
   - 找到 `var a` -> 初始化为 `undefined`。

### Step 2: 全局 EC 执行阶段

1. `a` 被赋值为 `10`。
2. 遇到 `foo(30)`，准备调用 -> 暂停全局 EC，开始创建 `foo` 的 EC。

### Step 3: foo EC 创建阶段 (压入栈顶)

1. **创建 AO**：
   - **Arguments**： `{0: 30, length: 1}`，形参 `i` 赋值为 `30`。
   - **函数声明**： 发现 `function d(){}` -> 提升，挂载到 AO。
   - **变量声明**： 发现 `var b` -> `undefined`；发现 `var c` -> `undefined`（函数表达式作为变量处理）。
2. **Scope Chain**： `[foo 的 AO, Global 的 VO]`。
3. **This**： 指向 `window` (普通调用)。

### Step 4: foo EC 执行阶段

1. `b` 被赋值为 `20`。
2. `c` 被赋值为那个匿名函数。
3. **执行 console.log**：
   - 找 `a`？AO 里没有 -> 去 Scope Chain 的下一层（Global）找 -> 找到了 `10`。
   - 找 `b`？AO 里有 -> `20`。
   - 找 `i`？AO 里有 -> `30`。
4. **结果**：`60`。

### Step 5: 销毁

1. `foo` 执行完毕 -> `foo` EC 弹出栈并销毁（除非有闭包）。
2. 控制权回到 Global EC。

## 总结

- **执行栈** 保证了代码的有序执行（单线程不乱套）。
- **执行上下文** 是代码执行的“小宇宙”。
- **创建阶段** 解释了为什么可以在声明前使用函数（因为完全提升），但不能使用 `var` 变量（因为只提升了名，值为 `undefined`）。
- **AO/VO** 实际上就是作用域的实体化表现。

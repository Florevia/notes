# session会话管理

## 为什么这里用 Map

  1. 场景分析
   - 会话是临时的，生命周期短，一旦结束就可以删除。
  2. 成本分析
  - 当前方案每次对话进10-50MB，对于一台16GB内存的服务器轻松应对现在的流量。
  - 如果用Redis，还要开一台Redis服务器，每次访问还有额外的网络请求，消耗带宽。
  3. 性能分析
  - map是内存读取，速度非常快
  - Redis有网络延迟
  4. 可靠性
   - 关键数据（问答，进度）保存到数据库
   - 临时数据（会话状态）保存到map

## Map vs Redis

  | 维度 | Map | Redis |
  | --- | --- | --- |
  | 存储位置 | 应用进程内存 | 独立服务内存 |
  | 性能 | 极快（本地） | 快，但有网络开销 |
  | 持久化 | 无，进程重启即丢 | 可配 RDB/AOF 持久化 |
  | 多实例共享 | 不支持 | 支持，天然共享 |
  | 扩展性 | 单机受限 | 可支撑更高并发/分布式 |
  | 运维成本 | 低 | 需要部署与运维 |

## 不适合用 Map 的场景
- 多实例部署（负载均衡）
- 需要数据持久化
- 需要在多个服务间共享数据
- 需要自动过期（TTL）
- 需要丰富的数据结构操作

## 使用场景

  1. Map：开发环境、PoC、单机部署、可丢失的临时状态。
  2. Redis：生产多副本、需要会话共享、服务重启后尽量保留状态、限流/分布式锁/队列等。

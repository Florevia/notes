# 人类行为验证

## 一、 前端实现 数据采集与加密 (Vue /原生 JS)

前端的核心任务是收集足够多的自然“噪音”。

1. 事件监听：在滑块上绑定 mousedown (开始)、mousemove (拖动)、mouseup (松开) 事件。

2. 轨迹数组生成：在 mousemove 事件中，不要每次移动都记录（数据量太大），可以做个节流（Throttle）或者按特定像素间隔采集。

3. 数据加密：使用 JS 的加密库（如 crypto-js）。当用户松开鼠标时，请求后端获取一个动态公钥（或者使用会话级别的动态 Token 作为密钥），将 trace 数组序列化后进行 AES 加密，再发送给后端。

## 二、 后端实现：图片生成与规则校验 (Node.js)

这部分是核心，一定不能把校验逻辑写在前端，否则形同虚设。

1. 动态图片生成 (防图像比对)黑客破解滑块的第一步通常是“找缺口”。

- 做法： 后端使用 Node.js 的图片处理库（如 sharp 或 canvas），每次请求验证码时，随机从图库里挑一张图，随机抠出一个拼图块（记录下真实的 X 坐标保存在服务端的 Redis/Session 中）。
- 下发： 将“带缺口的背景图”和“抠下来的拼图块”分别转成 Base64 发给前端。千万不要把真实的 X 坐标下发。

2. 后端规则引擎 (防机器轨迹)当收到前端发来的加密轨迹数据和最终滑动距离后，Node.js 后端解密出数组，按以下“规则”进行打分或拦截：

- 规则 1：目标吻合度（基础检验）

数组最后一位的 x 坐标，加上容错值（比如 $\pm 3$ 像素），是否等于后端生成的真实 X 坐标？如果不对，直接拒绝。

- 规则 2：Y 轴波动检验（防绝对直线）

人类的手腕是有生理构造限制的，在水平滑动时，Y 轴必然会有细微的上下波动（通常在 1~5 像素之间）。如果遍历数组发现所有的 y 值完全一致，说明是脚本写死的直线，直接拒绝。

- 规则 3：速度与加速度检验（防匀速运动）

遍历数组，计算相邻两点的速度：v = (x2 - x1) / (t2 - t1)。人类的习惯是“先加速、中间快、快到目标时减速微调”。如果算出来的速度 v 从头到尾基本保持不变（匀速），或者是完美的线性递增（简单的数学函数生成的轨迹），大概率是机器。

- 规则 4：时间检验

人类完成一次 200 像素的滑动通常需要 500ms 到 2000ms。如果 trace 数组显示总耗时只有 10ms，毫无疑问是接口被直接调用了。

# 封装组件的具体实现

## 核心原则

1. **单一职责**: 每个组件只做一件事。
2. **通用性**: 避免包含特定业务逻辑。
3. **可配置性**: 通过 Props 和 Slots 提供灵活性。

## 实现细节

### 1. Props (属性)

- 定义组件的输入。
- 使用 TypeScript 接口定义 Props 类型。
- 提供默认值。

```typescript
interface Props {
  title: string;
  visible?: boolean;
}
withDefaults(defineProps<Props>(), {
  visible: false,
});
```

### 2. Events (事件)

- 定义组件的输出。
- 使用 `defineEmits` 声明事件。

```typescript
const emit = defineEmits<{
  (e: "update:visible", value: boolean): void;
  (e: "confirm", data: any): void;
}>();
```

### 3. Slots (插槽)

- 提供内容分发机制。
- 使用默认插槽、具名插槽和作用域插槽。

### 4. Expose (暴露)

- 使用 `defineExpose` 显式暴露组件内部的方法或属性供父组件调用（如 `open()`, `close()`）。

```typescript
const open = () => {
  /* ... */
};
defineExpose({ open });
```

## 差异化场景配置

- **样式覆盖**: 提供 `class` 或 `style` props，或使用 CSS 变量。
- **配置对象**: 对于复杂组件，可以传入一个配置对象 `options`。
- **插槽**: 允许用户完全自定义某部分内容。

---

这是一个非常考验**组件设计能力**和**架构思维**的问题。作为一个资深前端工程师，在面试中回答这个问题时，不能只停留在 API 层面（props/emit），而应该从**设计原则**（SOLID）、**接口设计**以及**扩展性**三个维度来阐述。

我认为一个高质量的通用组件（比如 `ProTable` 或 `BusinessModal`）的封装应该遵循：**“默认好用，配置灵活，插槽兜底”** 的原则。

以下是我对组件封装的具体实现思路：

---

### 1. 核心接口设计：暴露哪些属性和方法？

组件的接口设计决定了它的易用性。我通常将接口分为 **数据 (Data)**、**交互 (Interaction)**、**UI 定制 (UI)** 和 **实例方法 (Instance Methods)** 四类。

#### A. Props (配置与数据)

Props 是组件的输入，设计时要区分“必须参数”和“可选配置”。

- **核心数据**：比如 Table 的 `dataSource` 或 `columns`。
- **状态控制**：比如 `loading`, `visible`, `disabled`。
- **配置对象 (Options)**：避免定义过多的扁平化 Props（如 `isRed`, `isLarge`, `hasBorder`...），建议合并为配置对象或枚举。
- _Bad:_ `showSearch={true}` `searchPlaceholder="xxx"`
- _Good:_ `search={ { placeholder: 'xxx', enterButton: true } }`

#### B. Events (事件与回调)

这是组件的输出，遵循 **单向数据流**。

- **标准事件**：`update:modelValue` (Vue 3 v-model), `change`, `click`。
- **业务钩子**：`onBeforeSubmit`（允许外部拦截或校验）, `onSuccess`, `onError`。

#### C. Slots (内容分发 - 扩展性的关键)

这是解决“差异化场景”的终极武器。

- **默认插槽**：主体内容。
- **具名插槽**：特定区域（如 `header`, `footer`, `toolbar`）。
- **作用域插槽 (Scoped Slots)**：这是高级封装的精髓。组件负责逻辑和数据，父组件负责渲染 UI。
- _场景_：Table 组件循环数据，但具体每一列长什么样（比如加个 Tag 或 按钮），通过作用域插槽抛出来让父组件决定。

#### D. Expose (实例方法)

在 Vue 3 中使用 `defineExpose` 显式暴露内部方法。这通常用于**命令式控制**。

- _场景_：
- 表单组件：`validate()`, `resetFields()`。
- 弹窗组件：`open()`, `close()`。
- 表格组件：`reload()` (刷新数据), `clearSelection()`。

### 2. 具体实现：以“通用搜索表格 (ProTable)”为例

这是面试中最能体现水平的案例。

#### Step 1: 定义 Props (配置化)

```typescript
// 伪代码/Vue3
const props = defineProps({
  // 1. 数据源：支持数组，也支持直接传入 API 函数（高级封装）
  request: {
    type: Function as PropType<(params) => Promise<any>>,
    required: true,
  },
  // 2. 列定义：包含字段名、以及搜索表单的配置
  columns: { type: Array, default: () => [] },
  // 3. 其他配置
  pagination: { type: [Boolean, Object], default: true },
});
```

#### Step 2: 处理插槽 (差异化渲染)

```html
<template>
  <div class="pro-table">
    <SearchForm v-if="search" :columns="columns" @search="handleSearch" />

    <div class="toolbar">
      <slot name="toolBar"></slot>
    </div>

    <el-table :data="tableData" v-loading="loading">
      <template v-for="col in columns">
        <el-table-column :prop="col.key" :label="col.title">
          <template #default="scope">
            <slot :name="col.key" :row="scope.row">
              {{ scope.row[col.key] }}
            </slot>
          </template>
        </el-table-column>
      </template>
    </el-table>
  </div>
</template>
```

#### Step 3: 暴露方法 (命令式调用)

```typescript
const reload = () => {
  // 重新调用 props.request 获取数据
  fetchData();
};

// 暴露给父组件，父组件通过 ref 调用 tableRef.value.reload()
defineExpose({ reload });
```

### 3. 怎么配置差异化的场景？

这是避免组件变成“屎山”（God Component）的关键。如果不处理好，组件会有几十个 `v-if`。

#### 策略一：配置优于硬编码 (Configuration over Hardcoding)

不要写死 `v-if="type === 'A'"`, 而是让外部传入配置。

- _场景_：表格有的需要复选框，有的不需要。
- _实现_：传入 `rowSelection` 对象配置，而不是 `showCheckbox` 布尔值。

#### 策略二：控制反转 (Inversion of Control) - 插槽

如果一个区域的 UI 变化极其多端（比如卡片的 Footer，有的是按钮，有的是文字，有的是进度条），**不要试图去配置它**，直接开一个 Slot。

- _原则_：**“如果你不知道这块区域长什么样，就把它交给使用者。”**

#### 策略三：Headless UI (无渲染组件)

针对逻辑非常复杂但 UI 差异巨大的场景（如日历、拖拽）。

- _实现_：组件只负责计算逻辑（日期计算、状态管理），通过 `Scoped Slot` 把数据和方法（`prevMonth`, `nextMonth`, `days`）抛出来。
- _优势_：UI 样式完全由使用者自定义，逻辑复用率 100%。

#### 策略四：透传 (Inheritance/Fallthrough)

对于组件内部封装的基础组件（如 `ProTable` 内部用了 `el-table`），使用 `v-bind="$attrs"` 和 `v-on="$listeners"` (Vue 2) 将父组件传递的未知属性直接透传给内部核心组件。

- 这样你不需要把 `el-table` 的 100 个 props 都在你的组件里重新声明一遍。

---

### 总结

对于组件封装，我的核心方法论是：

1. **Props 定义规范**：区分数据、配置和回调。
2. **方法显式暴露**：用 `defineExpose` 提供必要的命令式控制。
3. **插槽实现扩展**：用 Scoped Slots 实现“控制反转”，解决复杂 UI 差异。
4. **透传保证兜底**：利用 `$attrs` 保证底层组件的能力不丢失。

# 前端常用的鉴权方案

## 双 Token 机制 (Access Token + Refresh Token)

这是目前 SPA（单页应用）和移动端最标准的方案。

### 核心流程：

1. 登录 (Login)：
   - 前端 POST /login 发送账号密码。

   - 后端验证通过，返回两个 Token：
     - accessToken（比如 15分钟过期，含用户权限信息）。
     - refreshToken（比如 7天过期，仅用于换取新 Token）。

   - 前端将 Token 存入（推荐：内存存 Access，HttpOnly Cookie 存 Refresh，或者都存 Storage 视安全级别而定）。

2. 业务请求 (Request)：
   - 前端配置 Axios/Fetch 拦截器，在 Header 中加入 `Authorization: Bearer <accessToken>`。
   - 后端校验 Access Token 有效，返回数据。

3. 无感刷新 (Silent Refresh) —— 重点难点：
   - 触发：用户发起请求，Access Token 过期。

   - 拦截：后端返回 401 Unauthorized（带特定错误码）。前端响应拦截器捕获该错误。

   - 锁定：前端将当前状态标记为 isRefreshing = true，暂停后续所有业务请求，将它们放入一个 Promise 队列 中。

   - 刷新：前端携带 refreshToken 调用 /api/refresh-token 接口。

   - 重试：
     - 成功：拿到新的 Access Token，更新内存，遍历队列，用新 Token 重新发起之前失败的请求。
     - 失败（Refresh Token 也过期了）：清空本地存储，强制跳转登录页。

## OAuth 2.0 & OIDC (OpenID Connect)

这是企业级应用和第三方登录的标准。

### 标准流程 (授权码模式 Authorization Code)

这是目前最安全、最常用的流程（前端只负责跳转）：

1.  **重定向**: 用户点击"登录"，前端将浏览器重定向 (302) 到**认证中心 (Auth Server)**（如 Google 登录页）。

2.  **用户授权**: 用户在认证中心输入账号密码，并点击"允许"。

3.  **返回 Code**: 认证中心将页面重定向回前端的回调地址 (Callback URL)，并在 URL 参数中带上一个临时的 `code`。

4.  **换取 Token (后端完成)**: 前端把这个 `code` 发给**自己的后端**。后端拿着 `code` + `client_secret` 去找认证中心换取真正的 `access_token` 和 `id_token`。

5.  **建立会话**: 后端拿到 Token 后，验证身份，建立自己的 Session 或签发自己的 JWT 给前端。

## BFF (Backend for Frontend) 转发模式 —— 安全趋势

随着前端工程化深入，这是目前安全性最高的推荐方案。

- 痛点： 浏览器端存储 Token（Local Storage）容易被 XSS 攻击。
- 方案：
  - 前端（Browser）只跟 BFF 层（Node.js/Edge）通信，使用加密的 Session Cookie。
  - BFF 层持有真实的 JWT Token。
  - BFF 层负责 Token 的存储、刷新和转发给后端 API。
- 价值：将鉴权逻辑从不可信的浏览器端移到了可信的服务端（BFF），极大降低了 Token 泄露风险。

- 结果： 前端拿不到 Token，攻击者也就无法通过 JS 窃取，极大地提升了安全性。

## Cookie-Session 模式

这是浏览器原生支持最好的方案，前端代码量最少，但对跨域和 CSRF 防护要求高。

核心流程：

1. 登录 (Login)：
   - 前端 POST 账号密码。

   - 后端创建 Session，生成 sessionId。

   - 后端响应头包含 `Set-Cookie: session_id=xyz; HttpOnly; SameSite=Strict; Secure`。

2. 自动携带 (Auto-Send)：
   - 浏览器收到 Set-Cookie 后，自动将其保存在 Cookie Jar 中。

   - 后续前端发起同域请求时，浏览器自动将 Cookie 附加在 Request Header 中，前端 JS 代码无需做任何手动操作。

   - 注意：如果是跨域请求（Cross-Origin），前端需设置 withCredentials: true，且后端需配置 CORS 允许 Credentials。

3. CSRF 防御流程 (关键补充)：
   - 因为 Cookie 会自动发送，容易被 CSRF 攻击。

   - 前端在页面加载或登录时，会从后端获取一个 X-CSRF-TOKEN（通常在 Meta 标签或独立接口中）。

   - 前端拦截器将这个 Token 放入 HTTP Header（如 X-XSRF-TOKEN）中，后端验证 Cookie 和 Header 中的 Token 是否匹配。

> 总结：
> 如果是常规 C 端项目，首选 JWT 双 Token；如果是企业级中后台或对安全极其敏感的项目，我会推动后端或者自己搭建 BFF 层 来接管 Token 管理。

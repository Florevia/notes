# 第一部分：为什么 TCP 是可靠的？

1. 确认应答 (ACK) 与 超时重传 (Retransmission)
   - 机制：发送方发一个包，接收方必须回一个“收到(ACK)”。
   - 保障：如果发送方在规定时间内（RTO）没收到 ACK，它就默认包丢了，会重新发送。直到对方确认为止。

2. 序列号 (Sequence Number) —— 解决乱序与去重

- 机制：TCP 给每个数据包都编了号（Seq）。
  - 乱序重排：网络传输快慢不一，包到达的顺序可能是乱的。接收方根据序列号把包重新排好队，再给应用层。
  - 去重：如果接收方收到了重复的包（比如 ACK 丢了导致重传），根据序列号可以直接扔掉重复的。

3. 流量控制 (Flow Control) —— 照顾接收方
   - 机制：滑动窗口 (Sliding Window)。
     保障：接收方会告诉发送方：“我的缓冲区还能装多少数据（Window Size）”。发送方会根据这个大小控制发送速度。

4. 拥塞控制 (Congestion Control) —— 照顾整个网络
   机制：慢启动、拥塞避免、快重传、快恢复。
   保障：如果网络堵车了（丢包增多），TCP 会自动减慢发送速度，等路通了再加速，防止整个网络瘫痪。

## 有办法把 UDP 变成可靠的吗？

需要在 应用层 (Application Layer) 实现 TCP 的那套逻辑。

1. 如何实现？(RUDP - Reliable UDP)

   其实就是把 TCP 的核心特性搬到应用层代码里写一遍：
   - 加包头：在 UDP 数据包的身体（Payload）里，自己定义一个头部，放入 序列号 (Seq) 和 类型 (Type)。

   - 写逻辑：
     - 实现 ACK：收到 UDP 包后，应用层代码发回一个应用层的 ACK 包。
     - 实现重传：发送端维护一个定时器，没收到 ACK 就重发。
     - 实现排序：接收端建一个缓冲队列，按序列号排好序再处理。

## 直接用 TCP 不好吗？

它有 队头阻塞 (Head-of-Line Blocking) 问题。

- RUDP 的优势：
  - 灵活性：我想要“部分可靠”？比如视频直播，丢几帧没关系，关键帧重传就行。TCP 做不到，自定义 UDP 可以做到。
  - 速度：我可以去掉 TCP 繁琐的三次握手，结合 0-RTT 实现秒连。

### 业界的成熟落地案例

QUIC (HTTP/3) —— 最著名的案例
Google 搞出来的。它底层就是 UDP，但在上面通过软件层面实现了可靠传输、TLS 加密、流量控制。
它解决了 TCP 的队头阻塞问题，是下一代 Web 的标准。

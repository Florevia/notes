# TCP 粘包与拆包

## 概念

TCP 是 **面向流 (Stream Oriented)** 的协议，它是把数据看作一连串无结构的字节流，而**没有“包”的概念**。

- **粘包 (Sticky Packet)**： 发送方发送了两个数据包，接收方读到时，这两个包连在了一起，像粘住了一样。
- **拆包 (Packet Splitting)**： 发送方发送了一个大数据包，接收方收到时，它是被拆开成的两个或多个小包。

> 形象比喻：你往水管里连续倒了两杯水（两个包），水流出来时，你分不清哪部分是第一杯的，哪部分是第二杯的。

## 产生原因

1.  **TCP 的设计机制**：
    - TCP 并不了解上层业务数据的具体含义，它只负责把缓冲区里的字节流发送出去。

2.  **粘包原因**：
    - **Nagle 算法**（优化）：为了减少网络拥塞，TCP 会等待缓冲区攒够了一定大小的数据才发送。如果发送方连续发送几个小数据包，TCP 可能会把它们合并成一个大包发出去。
    - 接收方处理不及时：接收方缓冲区里的数据没来得及取走，后来的数据又到了，就粘在一起了。

3.  **拆包原因**：
    - **MSS 限制**：数据包大小超过了 TCP 的最大报文段长度 (MSS)，必须拆分开传输。
    - **缓冲区限制**：接收方的缓冲区满了，装不下整个包。

## 解决方案 (应用层处理)

既然 TCP 不管这个（它只保证数据按序到达），那就必须由 **应用层** 来划清界限。

1.  **定长协议 (Fixed Length)**：
    - 规定每个包固定长度（如 100 字节）。不够的补空格。
    - 简单但浪费空间。

2.  **特殊分隔符 (Delimiter)**：
    - 像 HTTP 协议那样，使用特殊符号（如 `\r\n`）作为包结束的标志。
    - 风险：如果内容里刚好也有这个分隔符，就会出错（通常需要转义处理）。

3.  **长度字段 (Length Field)** - **最推荐**：
    - 在应用层报文头中增加一个“长度”字段，告诉接收方数据有多长。
    - 接收方先读头部，解析出长度 `N`，然后再往后读 `N` 个字节。

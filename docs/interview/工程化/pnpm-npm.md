# npm 和 pnpm 的实现原理对比

- npm（扁平化 + 幽灵依赖）
- pnpm（内容寻址 + 硬链接 + 软链接 + 严格隔离）

## 详细的实现原理对比

### 1. npm 的实现原理 (从嵌套到扁平)

#### A. 早期痛点 (npm v2)

- 早期的 npm 使用的是 **嵌套结构**。

- 结构：如果 A 依赖 B，B 就会安装在 `node_modules/A/node_modules/B` 下。

> 问题：导致路径过长 以及大量的 **重复安装**（如果 C 也依赖 B，B 会被安装两次）。

#### B. 现在的机制 (npm v3+) - 扁平化 (Hoisting)

为了解决嵌套问题，npm v3 采用了 **扁平化策略**。

- 实现原理：
  - npm 会尽可能把所有依赖（包括子依赖）都 **提升（Hoist）** 到 `node_modules` 的根目录下。

  - 只有当遇到 **版本冲突** 时（例如 A 依赖 B v1.0，C 依赖 B v2.0），才会退回到 **嵌套模式**（其中一个版本在根目录，另一个在对应的子目录下）。

> 问题：幽灵依赖：因为所有依赖都被拍平到了根目录，你的项目代码可以直接 `import` 一个你并没有在 `package.json` 中声明的包。一旦你依赖的主包不再使用这个子包，或者升级了版本，你的代码就会莫名其妙地挂掉。

### 2. pnpm 的实现原理 (Symlink + Hard link)

核心机制可以概括为：

- 全局 Store
- 硬链接 (Hard link)
- 符号链接 (Symbolic link)

#### A. 内容寻址存储

- 原理：pnpm 不会将依赖直接下载到项目的 `node_modules` 下，而是下载到一个全局的仓库（Store，默认在 `~/.pnpm-store`）。

- 优势：
  - 全局去重：同一个版本的包，在整台电脑上只存储一份文件。如果是不同项目使用了同一个包，直接复用，磁盘空间极其节省。

  - 增量更新：不同版本的包如果只有 **部分文件不同，pnpm 甚至可以做到只存储不同的文件**（基于 hash）。

#### B. 链接机制

- 第一层：硬链接 (Hard Link)

在项目的 `node_modules/.pnpm` 目录下，pnpm 会通过 **硬链接** 指向全局 Store 中的文件。

> 硬链接就像是源文件的“分身”，它和源文件共享同一个磁盘物理块，修改一个另一个也会变，但不占用额外空间。

- 第二层：符号链接 (Symbolic Link / 软链接)

在项目的根 node_modules 下，**只会存放 `package.json` 中显式声明的依赖**。

这些依赖只是 **符号链接（快捷方式）**，指向 `node_modules/.pnpm/` 下对应的包。

而这个包的内部依赖（例如 A 依赖 B），会通过 **相对路径的符号链接**，指向 .pnpm/ 下的 B。

> 因为 `node_modules` 根目录下只有你声明的包，你无法 import 那些隐藏在 `.pnpm` 深处的子依赖。pnpm 强制建立了严格的依赖树。

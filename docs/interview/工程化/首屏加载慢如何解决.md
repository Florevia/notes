# 首屏加载慢

- 架构选型
- 工程化构建
- 网络传输优化
- 指标监控

以下是一套从底层到展现层的系统性优化方案：

### 一、 架构与渲染模式层

首屏慢的根本原因往往是 CSR 的先天缺陷：浏览器需要先下载庞大的 `JS bundle`，解析执行后才能渲染 DOM 并拉取接口数据。

1. **服务端渲染 (SSR) / 静态站点生成 (SSG)：**
* 如果项目对 SEO 和首屏极速呈现有强诉求，直接引入 `SSR（如 Vue 生态的 Nuxt）`。服务器直接返回拼接好的 `HTML 字符串`，后续再进行 `Hydration（注水）`接管交互。

1. **BFF (Backend for Frontend) 接口聚合：**
* 首屏常常面临 `请求瀑布流` 问题（一个接口依赖上一个接口的返回）。通过引入一层 `Node.js 中间层`（例如使用 NestJS），在服务端 `将首屏需要的多个零散接口聚合成一个请求返回给前端`，极大减少客户端的网络往返延迟 (RTT)。

3. **App Shell 模型：**
* 将页面的 `核心骨架`（Header、侧边栏、Loading 占位图）内联到 `index.html` 中。这样在 JS 下载和执行的真空期，用户能立刻看到页面框架，提升感知性能。

### 二、 工程化与构建层

构建工具的配置直接决定了产物体积。在使用 Vite 的生态中，精细化的 `拆包` 是核心。

1. **路由懒加载与组件异步引入：**
* 在 Vue Router 中严格遵守按需加载 `component: () => import('./views/Home.vue')`。
* 对于非首屏必须的重型组件（如复杂的富文本编辑器、图表库 ECharts），使用 Vue 3 的 `defineAsyncComponent` 进行异步加载。

2. **精细化分包策略 (Chunk Splitting)：**
* 默认情况下，Vite 会把所有的 `node_modules` 打包进一个巨大的 `vendor chunk`。需要通过配置 Rollup 的 `output.manualChunks` 将体积大且更新频率低的第三方库（如 Vue 核心、UI 组件库）单独抽离，利用浏览器强缓存。

3. **Tree-Shaking 与按需引入：**
* 确保依赖的库支持 ES Modules。配合 `unplugin-vue-components` 等插件实现 UI 组件库的自动按需引入，剥离无用代码。

4. **产物压缩：**
* 在构建阶段开启 Gzip 或更高效的 Brotli 压缩（通过 `vite-plugin-compression`），配合 Nginx 服务器的解压配置，通常能将静态资源体积缩减 60% 以上。

### 三、 网络与传输层 

1. **资源提示符 (Resource Hints)：**
* 利用 `<link rel="preload">` 提前加载首屏关键资源（如核心字体、关键 CSS、首屏大图）。
* 利用 `<link rel="prefetch">` 在浏览器空闲时预加载下几个页面可能用到的资源。

2. **CDN 分发与边缘计算：**
* 将静态资源全部上 CDN，让用户从地理位置最近的节点获取数据。

3. **HTTP/2 或 HTTP/3：**
* 开启 `HTTP/2 多路复用`，突破浏览器对同一域名并发请求数的限制（通常是 6 个）。

### 四、 运行时与监控层

1. **图片与媒体优化：**
* 首屏图片使用 WebP 或 AVIF 格式。
* 非首屏区域的图片严格落实懒加载 (`loading="lazy"` 或基于 `IntersectionObserver` 的自定义实现)。

2. **建立性能监控闭环：**
* 任何没有数据支撑的优化都是盲人摸象。通过接入 `Web Vitals 指标体系`，重点监控 `**LCP (最大内容绘制)** 和 **FID (首次输入延迟) / INP (交互到绘制)**`。
* 使用 `Chrome DevTools` 的 `Performance 面板`和 `Lighthouse` 定期对系统进行压测。

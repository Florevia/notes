### 1. 数据模型相关的术语

- **Schema（模式）**：你可以把它理解为**“数据的设计图纸”或“表格的表头”**。
- **固定 Schema**：像严谨的 Excel 表格。在存数据之前，你必须先规定好第一列叫“姓名”、第二列叫“年龄”。如果突然想存一个“爱好”，你必须先修改整个表的结构（加一列），才能存进去。
- **Schema 灵活**：像一个随便装东西的档案袋。今天你可以存带有“姓名”和“年龄”的档案，明天你可以直接塞进一个带有“星座”和“宠物名字”的档案，数据库不会报错。

- **主键 (Primary Key)**：每行数据的**“唯一身份证号”**。比如学生的学号，绝对不会重复。
- **外键 (Foreign Key)**：用来**“牵线搭桥”**的线索。比如在“成绩表”里存一个“学生学号”，这个学号就是外键，它指向“学生表”里的那个学生，把两张表关联了起来。
- **JSON / BSON**：
- **JSON**：一种非常流行的数据格式，长得像字典。比如 `{"姓名": "张三", "年龄": 20}`。人类很容易看懂。
- **BSON**：MongoDB 等文档型数据库在底层实际存储时用的格式。它把 JSON 变成了二进制（计算机读得更快），而且支持更多的数据类型（比如日期、二进制数据）。

- **嵌套对象和数组**：在关系型数据库里，格子里面只能放一个值（比如“张三”）。但在文档型数据库里，格子里可以套娃。比如“联系方式”这一项里，可以再嵌套一个列表 `["电话1", "电话2", "微信"]`。

### 2. 查询方式相关的术语

- **JOIN（连接 / 连表查询）**： 把分散在多张表里的数据“拼”成一张完整大表的动作。比如，把“用户表”和“订单表”通过用户 ID 拼接起来，看看张三买了什么。关系型数据库做这个非常拿手。
- **聚合 (Aggregation)**：数据的**“统计汇总”**。比如算出全班的平均分、找出销售额最高的商品、统计每个省份的用户数量。
- **反范式 (Denormalization)**：
- 先理解“范式”：关系型数据库追求“不重复”，比如商品名称只在“商品表”存一次，订单表里只存商品 ID。这叫符合范式。
- **反范式**：为了**查询快**，故意把数据冗余存放到一起。比如在文档型数据库的订单里，直接把“商品名称”和“价格”存进去。这样看订单的时候，一口气就能读完，不需要去别的表（集合）里找了（这就是所谓的**减少跨集合关联**）。

### 3. 一致性与事务相关的术语

- **ACID 事务**：保证一组操作**“同生共死”**的机制。最经典的例子是银行转账：你扣了 100 块（操作 A），朋友账户加了 100 块（操作 B）。ACID 保证这两个操作要么全成功，要么遇到故障时全撤销，绝对不会出现你扣了钱但朋友没收到的情况。关系型数据库对这个支持得极好。
- **单文档原子性**：**“原子性”就是不可分割**。意思是说，哪怕你的一个文档里嵌套了非常复杂的数据，当你去更新它时，数据库保证这一整条更新要么彻底成功，要么彻底失败，不会出现“只改了一半”的乱象。
- **强一致**：你刚存进去的数据，下一秒去查，一定能查到最新存入的那个值。不会出现“数据还没同步过来，查到了旧数据”的延迟感。

### 4. 扩展与演进相关的术语

- **横向扩展 (Horizontal Scaling)**：

```
* 如果数据库扛不住了，你可以花大价钱去买一台更贵的超级电脑（这叫纵向扩展）。
* **横向扩展**则是买多台便宜的普通服务器，把它们连成一个集群，让大家分摊工作量。文档型数据库因为数据之间关联少，天生更容易做横向扩展。

```

- **半结构化数据**：介于“完全规整的表格”（结构化）和“纯文本文章/视频”（非结构化）之间的数据。比如日志、爬虫抓取回来的网页信息、用户的聊天记录，有一定格式，但长短不一、字段不固定。
- **混合架构**：成年人不做选择，全都要。在一个大型系统里，把核心的“钱”相关的数据存进 MySQL（关系型），把用户平时浏览留下的痕迹、日志、配置信息存进 MongoDB（文档型），各自发挥长处。

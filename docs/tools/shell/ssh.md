# SSH 远程连接

## 是什么

SSH（Secure Shell）是一种加密的远程登录与命令执行协议，用来在不可信网络上安全地操作另一台机器。

默认走 **TCP 22 端口**，在客户端与服务器之间建立加密通道，认证和数据都走这条通道。

一句话：SSH 就是「加密的远程终端」，也是运维、开发里连服务器、配 Git、做隧道的基础工具。

## 解决什么问题

早期远程工具不加密：

- **Telnet**：远程登录（默认 23 端口），账号密码和命令都是明文。
- **rsh（remote shell）**：远程执行命令，同样基本明文。

SSH 用加密通道 + 身份认证替代它们，避免中间人直接看到密码和会话内容。

## 常见用途

- 远程登录服务器（`ssh user@host`）
- 在远程机器上执行命令（`ssh user@host 'cmd'`）
- 安全传文件（`scp` / `sftp`）
- 端口转发 / 隧道
- Git 等工具的认证与传输（如 `git@github.com:...`）

## 基本工作方式

1. 客户端连上服务器（默认端口 22）
2. 协商加密算法，建立安全通道
3. 身份认证（密码，或更常见的公钥 / 私钥）
4. 之后的 shell、传文件、转发都在加密通道里进行

## SSH-2 的三层协议架构

SSH-2 不是单一协议，而是由三个子协议分层协作。一次连接大致经过五个阶段：

1. **建立 TCP 连接并交换版本**：客户端连接服务器 22 端口，双方确认使用 SSH-2。
2. **算法协商**：协商密钥交换、加密、MAC、压缩等算法。
3. **密钥交换与服务端身份验证**：通过 DH（Diffie-Hellman）交换生成会话密钥，客户端用服务器的主机密钥验证其身份。
4. **用户认证**：客户端向服务器证明自己的身份，支持密码、公钥、键盘交互等方式。
5. **进入连接协议**：在加密隧道中打开一个或多个逻辑通道，运行 Shell、SFTP/SCP、端口转发、X11 转发等。

| 协议层 | 核心职责 | 对应阶段 |
| --- | --- | --- |
| 传输层协议（SSH Transport Layer） | 运行在 TCP 之上；负责版本与算法协商、DH 密钥交换、服务端身份验证，提供加密、完整性校验和数据压缩 | 1–3 |
| 用户认证协议（SSH User Authentication） | 运行在传输层之上；负责向服务端验证客户端用户的合法身份，支持密码、公钥、键盘交互等 | 4 |
| 连接协议（SSH Connection Protocol） | 运行在认证层之上；实现多路复用（Multiplexing），把单一加密隧道拆分为多个逻辑通道（Channel） | 5 |

```text
TCP
 └── 传输层：加密、完整性校验、压缩、服务端身份验证
      └── 用户认证层：确认客户端用户身份
           └── 连接层：多路复用
                ├── Channel：交互式 Shell
                ├── Channel：SFTP / SCP
                ├── Channel：本地 / 远程端口转发
                └── Channel：X11 图形转发
```

得益于连接协议的多路复用，建立一条 SSH 连接后，不仅可以在里面打开交互式 Shell，还能在同一条加密隧道中同时进行 SFTP/SCP 文件传输、本地/远程端口转发（SSH 隧道）以及 X11 图形界面转发，无需为每个任务重新握手加密。

一句话记忆：**传输层负责把管道建好并加密，用户认证层负责确认“你是谁”，连接层负责在这根管道里同时跑多个任务。**

## 公钥认证

常用 **公钥认证**，比每次输密码更安全、也更适合自动化：

| 位置 | 文件 | 作用 |
| --- | --- | --- |
| 本机 | `~/.ssh/id_ed25519`（私钥） | 证明「我是我」，勿泄露、勿上传 |
| 本机 | `~/.ssh/id_ed25519.pub`（公钥） | 可以给人、可以拷到服务器 |
| 服务器 | `~/.ssh/authorized_keys` | 存放允许登录的公钥列表 |

生成密钥（推荐 ed25519）：

```bash
ssh-keygen -t ed25519 -C "your@email.com"
```

把公钥拷到服务器（任选其一）：

```bash
ssh-copy-id user@host
# 或手动：把 .pub 内容追加到服务器 ~/.ssh/authorized_keys
```

登录时客户端用私钥做证明，服务器用 `authorized_keys` 里的公钥校验，通过即可进 shell。

## 基本操作

### 登录

```bash
ssh username@hostname
# 非 22 端口
ssh -p 2222 username@hostname
# 登上去直接跑一条命令（跑完退出）
ssh username@hostname 'hostnamectl'
```

首次连接会提示确认主机指纹，确认后写入 `~/.ssh/known_hosts`，用来防主机被掉包（MITM）。

### 传文件（走 SSH 通道）

```bash
# 本地 → 远程
scp -r /path/to/local user@host:/path/to/remote

# 远程 → 本地
scp -r user@host:/path/to/remote /path/to/local

# 非 22 端口用 -P（大写）
scp -P 2222 file user@host:/tmp/
```

交互式文件操作用 `sftp user@host`。

### 配置别名（`~/.ssh/config`）

避免每次敲长命令：

```text
Host myserver
    HostName 1.2.3.4
    User ubuntu
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

之后直接：

```bash
ssh myserver
scp ./dist myserver:/var/www/
```

## 端口转发（SSH 隧道）

### 核心本质

面试记一句即可：**SSH 隧道 = 把任意 TCP 流量封装打包进已建立且加密的 SSH 连接（默认 22 端口）中传输。**

主要解决两大场景问题：
1. **突破网络隔离**：防火墙仅放行 22 端口，目标服务端口（如 3306、8080）被隔离在内网无法直连。
2. **通信安全加固**：为明文传输的协议（如 HTTP、早期数据库连接等）套上一层端到端加密外壳。

---

### 三种转发模式对照

| 类型 | 参数 | 监听端口位置 | 流量流向 | 典型命令 | 核心用途 |
| --- | --- | --- | --- | --- | --- |
| **本地转发** | `-L` | **本地客户端** | 本地 → SSH 隧道 → 远程目标 | `ssh -L 8080:127.0.0.1:80 user@host` | 把远程/内网服务“拉到”本地访问 |
| **远程转发** | `-R` | **远程服务器** | 远程 → SSH 隧道 → 本地服务 | `ssh -R 9000:127.0.0.1:3000 user@host` | 把本地服务“推到”远程公网暴露（内网穿透） |
| **动态转发** | `-D` | **本地客户端** | 本地 SOCKS → SSH 隧道 → 动态目标 | `ssh -D 1080 user@host` | 本机开 SOCKS5 代理，任意流量经远程发出 |

---

### 1. 本地端口转发（`-L`）

> **口诀**：监听开在**本地**，把远程服务拉到本地来访问。

* **命令格式**：`ssh -L 本地端口:目标主机:目标端口 user@SSH服务器`
* **数据流向**：
  ```text
  访问 localhost:8080 
    ──> 本机 SSH 客户端（打包加密）
    ──[SSH 隧道]──> 远程 host（解包）
    ──> 目标 127.0.0.1:80（相对 host 而言的目标服务）
  ```
* **典型场景**：
  * **直连内网数据库**：生产/测试机上的 MySQL（3306）仅监听 `127.0.0.1` 且无公网访问权限。执行：
    ```bash
    ssh -L 13306:127.0.0.1:3306 user@remote-host
    ```
    本地使用 Navicat / DBeaver 连接 `localhost:13306` 即可直接操作该数据库。
  * **跳板机穿透内网 Web 面板**：通过跳板机访问内网另一台服务器的控制台：
    ```bash
    ssh -L 8080:192.168.1.50:80 user@jump-server
    ```

---

### 2. 远程端口转发（`-R`）

> **口诀**：监听开在**远程**，把本地服务推到远程暴露（自建简易 frp / ngrok 内网穿透）。

* **命令格式**：`ssh -R 远程端口:目标主机:目标端口 user@公网SSH服务器`
* **数据流向**：
  ```text
  外部请求 host:9000 
    ──> 远程 host 的 SSHD（打包加密）
    ──[SSH 隧道]──> 本机 SSH 客户端（解包）
    ──> 本机 127.0.0.1:3000（本地开发服务）
  ```
* **典型场景**：
  * **本地联调第三方回调**：本地开发微信支付、GitHub Webhook 等接口（运行在 `localhost:3000`），无公网 IP 无法接收回调通知。执行：
    ```bash
    ssh -R 9000:127.0.0.1:3000 user@public-vps
    ```
    将第三方平台回调地址填为 `http://public-vps:9000/callback`，请求即可直接进入本地机器断点调试。
  * **注意细节**：远程机器默认仅将端口绑定在回环地址 `127.0.0.1`。若要允许公网所有机器直接访问该转发端口，需在远端 `/etc/ssh/sshd_config` 中配置：
    ```text
    GatewayPorts yes
    ```

---

### 3. 动态端口转发（`-D`）

> **口诀**：本地开启标准 **SOCKS5 代理**，目标地址与端口无需写死，按需动态转发。

* **命令格式**：`ssh -D 本地端口 user@SSH服务器`
* **典型示例**：
  ```bash
  ssh -D 1080 user@remote-host
  ```
* **机制与场景**：
  * `-L` 与 `-R` 必须在启动前固定目标 IP 和端口；而 `-D` 在本地启动一个遵循 SOCKS5 协议的代理端口。
  * 浏览器或操作系统网络代理配置为 `socks5://127.0.0.1:1080` 后，你的所有流量都会经由该 SSH 服务器代为发出。
  * 适合作为轻量级网络代理，或者一次性访问远端内部机房的所有内网网站与系统，免去针对每个系统配置一条 `-L`。

---

### 4. 隧道运维常用参数组合

在后台维持一条纯转发隧道时，通常使用以下参数组合：

```bash
ssh -C -N -f -L 8080:127.0.0.1:80 user@host
```

* `-N`：**不执行远程命令 / 不打开 Shell**（仅建立端口转发通道）。
* `-f`：在后台运行（Background），认证完成后立刻将终端控制权还给用户。
* `-C`：开启**数据流压缩**（慢速网络下可提升吞吐速度）。

## 和 Git 的关系

`git@github.com:user/repo.git` 这种地址走的是 **SSH 协议**，不是 HTTPS：

- 用你本机私钥认证（公钥要加到 GitHub / GitLab）
- 传代码内容也在 SSH 加密通道里

代理 / TUN / fake-IP 把 `github.com` 解析成 `198.18.*` 时，SSH（22）容易出问题，见 [System Proxy / TUN / fake-IP](/tools/developer-tools/proxy-tun-fake-ip)。

## 常见问题

| 现象 | 常见原因 |
| --- | --- |
| `Permission denied (publickey)` | 没用对私钥、服务器没放公钥、权限不对（私钥建议 `600`，`.ssh` 目录 `700`） |
| `Host key verification failed` | `known_hosts` 里旧指纹和当前主机不一致（重装过系统或真被劫持，需确认后再更新） |
| `Connection refused` / 超时 | 22 端口没开、安全组/防火墙拦了、sshd 没起、地址错了 |
| 一直要密码 | 没配公钥，或 `ssh -v` 看发现没用上你以为的那把密钥 |

排障常用：

```bash
ssh -v user@host          # 详细握手日志
ssh -i ~/.ssh/某私钥 user@host
```

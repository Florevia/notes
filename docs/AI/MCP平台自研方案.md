# 企业内部 MCP 平台自研方案(代号 ToolHub)

> 调研时间:2026-10;结论基于对 Composio、Obot、IBM ContextForge、Higress、LiteLLM 的实际调研。
> 关联笔记:[[MCP]](协议本身的知识笔记)

## 一、背景与目标

公司现状:

- 员工在各类 Agent 客户端(Cursor / Claude Code / Cline 等)中使用多个采购的 MCP 服务和内部 MCP server;
- 每个人要在**每个客户端**里**逐个**配置 MCP,重复且易错;
- 不同员工可用的工具不同,目前没有统一的权限分配机制;
- 无法回答"谁在什么时候用了什么 MCP、传了什么参数"。

平台目标(按优先级):

1. **统一入口**:全员只配一个网关地址 + 个人凭证,一次配置;
2. **权限治理**:server 级 + 工具级权限,支持审批开通和按部门自动开通;
3. **调用审计**:谁、何时、用了哪个 MCP 的哪个工具、什么参数(不含提示词——提示词不经过 MCP 通道,明确不做);
4. **上下文友好**:不把全部工具定义塞进模型上下文,提供工具搜索(元工具模式);
5. **可扩展**:内部新开发的 MCP server 能低成本上架。

明确不做:提示词审计(需要 LLM 代理层,已决策砍掉)、沙箱代码执行、触发器/webhook 投递、对外多租户。

边界条件:身份源为**钉钉**(扫码登录 + 审批流);当前用户 <100,未来会超过(自研无人数授权约束,这正是选自研的原因之一)。

## 二、调研结论摘要(为什么自研)

### 2.1 市场上已有什么

| 项目 | 定位 | 与本需求的差距 |
| --- | --- | --- |
| **Composio** | AI Agent 集成平台(1000+ 应用工具 + OAuth 托管 + 触发器 + 沙箱) | 开源的只有 SDK/CLI,平台后端闭源托管;且能力远超所需,场景不匹配 |
| **Obot** | 企业 AI 治理平面 + MCP 网关,功能与本需求匹配度最高(vMCP、工具搜索、审批、审计、Sentry 设备端) | 社区版限 100 用户,超出需 Enterprise 授权(询价);无钉钉身份源 |
| **IBM ContextForge** | Apache-2.0 MCP 网关/注册表/代理,无人数限制 | 审批、钉钉、报表需自建 |
| **Higress + HiMarket** | 国内开源 AI 网关 + 私有 MCP 市场 | 审批/审计产品化弱,二开量大 |
| **LiteLLM** | LLM 网关为主 + MCP 权限 | 无目录/审批;核心优势(提示词审计)本需求不需要 |

### 2.2 三条路线的账

| 路线 | 工期(2人小队) | 成本 | 主要风险 |
| --- | --- | --- | --- |
| Obot 二开 | 6-9 周 | 3-5 人月 + 超员后企业授权费 | 授权费不可控;无钉钉支持需自写 provider |
| ContextForge/Higress 二开 | 2-3 个月 | 5-7 人月 | 治理功能大半自建,还是"二开" |
| **从零自研(本方案)** | **15 周** | **7-10 人月** | 协议演进、兼容矩阵需自己扛 |

**决策:从零自研。** 理由:①无人数授权约束;②钉钉身份与审批是一等公民;③需求边界清晰(砍掉 Composio 的重能力后,自研范围可控);④核心资产(权限模型、元数据规范、审计数据)完全自主。架构上仍参考 Composio(session + 元工具)与 Obot(vMCP、治理思想)的公开设计。

## 三、关键设计决策

### 决策 1:单端点 + 混合加载

每个员工只配一个地址 `https://mcp.corp.cn/mcp`。网关对该端点暴露的 `tools/list` 是混合的:

- **常用工具直出**:用户权限内、标记为"高频"的工具以真实定义(完整 JSON Schema)直接出现,工具名加服务前缀防碰撞(如 `github__create_issue`),Agent 拿到即可调用;
- **长尾走元工具**:额外提供 3 个元工具——
  - `search_tools(query)`:在**该用户有权限的工具池**内检索,返回 id/名称/一句话摘要;
  - `get_tool_schema(tool_id)`:按需取完整参数定义;
  - `call_tool(tool_id, args)`:执行(二次鉴权后转发上游)。

好处:弱模型靠常用集也能干活,强模型靠搜索覆盖全量,上下文永不爆炸;规避纯搜索懒加载"描述相近拿错 schema"的已知问题。此模式已被 Composio(meta tools)与 Cloudflare(Code Mode)生产验证。

### 决策 2:网关对上游只说 HTTP,stdio 用适配器隔离

上游 MCP server 仅两种形态:采购的 SaaS MCP(HTTP)、内部 MCP(要求 HTTP)。stdio 类(如 npx 包)统一用一个小适配容器包成 HTTP 再接入。

理由:stdio 是"每网关实例各自起子进程",多副本部署、健康检查、重启策略全是坑;上游统一 HTTP 后,网关本身完全无状态、可水平扩。

### 决策 3:技术栈

| 组件 | 选型 | 说明 |
| --- | --- | --- |
| 网关 | Go(官方 MCP go-sdk) | 单二进制部署内网极简;代理类负载并发模型合适。团队若 JS 重度,可换 TS + 官方 SDK,架构不变 |
| 存储 | PostgreSQL 16(+pgvector) | 全部业务数据 + 审计;语义检索后期加,不引入额外数据库 |
| 缓存/会话 | 进程内缓存起步 → Redis(规模化后) | 策略缓存、限流、多副本会话 |
| 前端 | 管理台 amis(低代码)+ 员工门户极简 React | 表单/表格密集场景开发量减半 |
| 部署 | Docker Compose(MVP)→ K8s(规模化) |  |

### 决策 4:钉钉扫码换 API Key,MCP OAuth 后补

员工在门户钉钉扫码 → 平台验证身份建号 → 自助生成**个人 API Key**(粘到客户端 Bearer 头,一次配置)。MCP OAuth 2.1 server 模式作为二期可选(体验更顺但客户端兼容矩阵更费,不挡 MVP)。审批走钉钉原生审批流,通过后自动写权限。

读图要点:

- **网关是纯无状态的"策略执行点"**:一切状态(用户、权限、目录、审计)都在 Postgres,扩容 = 加副本;
- **钉钉是唯一身份与审批源**:平台不自建密码体系,账号生命周期自动跟随钉钉(离职即失效);
- **上游全部 HTTP 化**:内部系统接入门槛降到最低。

## 五、数据模型(核心表)

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | id, dingtalk_union_id, name, email, status | 钉钉扫码自动建号;通讯录同步停用离职账号 |
| `groups` / `user_groups` | 组、组成员 | 从钉钉部门/通讯录同步 |
| `mcp_servers` | slug, transport, endpoint, 加密凭据, owner_team, status, health | 每个上游一条;owner 字段是治理关键 |
| `tools` | server_id, name, 描述(中/英), 参数 JSON Schema, 敏感级别, schema_hash, 检索列 | 目录同步任务自动维护;schema 变更触发元数据质量门禁 |
| `policies` | subject(用户/组), server_id, tool_id(空=整服务), effect, source | **allow 清单制,deny 优先**;source 标记来自审批/自动规则/默认 |
| `auto_rules` | group_id → server_id | "研发部自动开通 GitHub"这类零审批规则 |
| `requests` | user_id, 目标, 理由, status, 钉钉审批实例 id | 审批状态机,与钉钉回调对账 |
| `audit_logs` | ts, user_id, client, server, tool, 脱敏后参数, 结果状态, 耗时, request_id | **按月分区**,异步写入;180 天热数据 + 归档 |
| `api_keys` | user_id, key_hash, scopes, 过期时间 | 员工门户自助生成/吊销 |

## 六、核心流程

### 流程 1:员工首次接入(一次性成本约 2 分钟)

```text
员工 ──► 门户点"钉钉扫码" ──► 钉钉授权 ──► 平台建号/登录
     ──► 门户展示: 网关地址 + [生成API Key] 按钮
     ──► 复制页面上的 Cursor/Claude Code/Cline 配置片段(带 Key)
     ──► 粘进客户端 ──► 完成,以后换新工具不再碰客户端配置
```

### 流程 2:Agent 拿工具列表(每次会话开始)

```text
Agent ── tools/list ──► 网关
  网关: 验Key → 取用户策略(缓存60s) → 组装
        [github__create_issue, github__star_repo, ...(高频直出)]
        + [search_tools, get_tool_schema, call_tool]
Agent ◄── 可见工具 = 权限过滤后的常用集 + 3个元工具
```

### 流程 3:长尾工具的搜索-取schema-调用

```text
Agent ── call search_tools("发周报到钉钉群")
  网关: 在该用户有权工具池内检索 → 返回 top5 摘要(id/名称/一句话)
Agent ── call get_tool_schema(tool_id="dingtalk_42")
  网关: 返回完整 JSON Schema(参数/说明/示例)
Agent ── call call_tool(tool_id, args={...})
  网关: 二次鉴权 → 限流 → 转发上游 → 结果回传
        └─ 异步: 审计落库(人/时间/工具/脱敏参数/耗时)
```

### 流程 4:权限申请(审批或自动通过)

```text
员工 ──► 门户/Agent提示"无权限,去申请" ──► 创建 request
  ┌─ 命中 auto_rules(如"研发部→GitHub 自动开通")─► 立即写 policy,秒开
  └─ 未命中 ──► 调钉钉审批API创建实例 ──► 审批人在钉钉里点通过
              ──► 钉钉回调网关 ──► 写 policy ──► 门户/IM通知员工
        (回调丢失兜底:每5分钟对账轮询审批状态)
```

### 流程 5:内部新 MCP server 上架

```text
内部团队门户提交(名称/transport/endpoint/凭据/描述/负责人)
  → 管理员审核(或命中自动上架规则)
  → 目录同步任务: tools/list 拉取 → schema_hash 比对
  → 元数据质量门禁(见第八节,LLM 反推审核,不过打回)
  → 入检索索引 → 可分配权限/进入目录
  → 持续: 健康检查、下线/版本管理
```

## 七、安全设计(底线项)

1. **凭据保险箱**:上游 MCP 的 API key/OAuth 凭据信封加密(主密钥存 KMS 或加密配置,每服务独立数据密钥),内存解密,日志永不打印;
2. **参数脱敏**:审计入库前过正则银行(身份证/手机号/密码字段);敏感级工具可配置"仅记录元信息不记录参数";
3. **权限双重执行**:`tools/list` 过滤(看不见)+ `tools/call` 拦截(调不动),防绕过;
4. **管理动作全审计**:谁改了谁的权限、谁审批的,全留痕;
5. **三维限流**:用户/服务/工具,防个别人烧光采购配额;
6. 网关只部署内网,TLS 终结在 Nginx。

## 八、配套运营制度(平台成败的一半)

### 8.1 元数据规范(决定工具搜索质量的上限)

1. **命名**:动词_名词式(如 `查询客户订单` / `QUERY_CUSTOMER_ORDER`),禁止 `tool1`、`api_v2`;
2. **工具描述三段式**:一句话功能 + 适用场景 + **不适用/边界**(边界写清能显著降低误配率);
3. **中英双语**:员工用中文搜,模型索引可能偏英文,两种都写;
4. **参数级说明**:每个参数写含义、格式、示例值(搜索命中后模型填参也靠它);
5. **质量门禁**:上架时用 LLM 自动审——把工具描述给模型反推"这是干嘛的",推不出/推错就打回重写;
6. **Owner 制 + 评测集**:每个 MCP server 挂负责人;收集 20-50 条员工真实问法做回归测试集,每次上架新工具跑一遍防劣化。

### 8.2 权限运营

- 自动规则优先:按部门/组配默认开通,减少审批噪音;
- 审批 SLA:超 24 小时未处理自动提醒;高频申请反向沉淀为自动规则;
- 每季度权限盘点:清理长期未使用的授权(审计数据可直接支撑)。

## 九、里程碑(2 人:1 后端 + 1 全栈)

| 阶段 | 周 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| **M0 内核验证** | 1-2 | go-sdk 技术验证:最小网关代理 2 个上游(1 采购 + 1 内部) | Cursor/Claude Code/Cline 三端连通,输出协议兼容清单 |
| **M1 MVP** | 3-7 | 鉴权(API Key + 管理员分配)、RBAC、审计落库、混合 tools/list、关键词版元工具、最小管理台 | 10 个真实员工用起来;审计能查"谁何时调了什么" |
| **M2 治理完整** | 8-11 | 钉钉扫码 + 通讯录/组同步、审批流对接 + 自动规则、员工门户、pgvector 语义检索、元数据质量门禁、报表 | 全员自助接入;审批闭环;中文问法搜索命中可用 |
| **M3 规模化** | 12-15 | 多副本 + 会话外置(Redis)、审计分区归档、压测、安全加固、运维文档 | 支撑全员;故障演练通过 |

总计 15 周(约 4 个月)出完整版;**MVP 第 7 周即可让首批员工真实使用**——先让平台在真实使用中长出需求,M2/M3 按实际反馈调整。

成本估算:开发 7-10 人月(约 25-40 万,按 3-5 万/人月);基础设施 2 台 4C8G 内网虚拟机起步;上线后维护 0.5 人力。

## 十、风险与对策

| 风险 | 对策 |
| --- | --- |
| MCP 协议演进快(v2 无状态重写进行中) | M0 锁 go-sdk 版本;抽象内部 `ToolProvider` 接口,协议变更只动适配层 |
| 客户端兼容矩阵比预期费 | M0 提前把三大客户端的握手/头/会话行为写成 checklist 持续维护 |
| 审计表膨胀 | 上线第一天就按月分区 + 归档策略,不等出问题再改 |
| 上游 stdio 生态包不配合 | 适配器 sidecar 模式隔离,网关永远只见 HTTP |
| 两个人力被日常需求冲掉 | M1 后冻结新功能两周只修 Bug,保首批用户口碑 |
| 搜索质量不达预期 | 元数据规范 + 质量门禁制度性兜底;关键词不够上 pgvector 语义检索 |

# 针对面试的问题

## 1. 项目介绍

简历：独⽴负责商业级 AI ⾯试平台研发，基于 `LangChain + NestJS` 落地，实现了 SSE 流式交互与 Agent 智能决策

- 这个项目是一个 AI 面试 SaaS 平台的后端，基于 `NestJS + LangChain + MongoDB` 落地，核心业务是三条线：简历押题、专项模拟面试、综合面试评估。

### 项目亮点

- 流式交互体验做得比较完整
  通过 `SSE + RxJS` 做了逐字流式输出，前端能实时看到“追问/参考答案/进度事件”，并处理了 `X-Accel-Buffering`、`flush` 等细节，交互上接近 Chat 类产品。

  > - 控制器层把接口做成标准 SSE：设置 `text/event-stream`、`X-Accel-Buffering: no`、按 chunk `res.write(...)`、可用时 `flush()`、客户端断开时 `unsubscribe()` 防泄漏。
  > - 服务层用 `Subject` 推送进度事件，用 `AsyncGenerator` 逐字产出问题；并把问题流和参考答案流拆成不同事件类型（`QUESTION/REFERENCE_ANSWER/WAITING`），前端可以精细渲染。

- 长会话状态管理和断点恢复
  面试过程不仅在内存里维护，还把 sessionState 持久化到 MongoDB，支持 `pause/resume/end`，浏览器中断后可以恢复上下文继续问答。

  > 会话采用 **内存 + 持久化** 双轨：`内存 Map` 保证实时交互性能，Mongo 的 `sessionState` 保证可恢复。每轮问答都会同步更新 `qaList 和 sessionState`；`pause 会写状态并清理内存`，`resume 从数据库恢复会话重新激活`，`end 做收口并清理`。

- 工程化和可观测性
  全局异常过滤、统一响应、`TraceId 链路日志`、`Prometheus 指标`（请求量/耗时/错误/AI 调用）都有，线上排障和性能分析比较可控。

  > 入口层有全局 **ValidationPipe、统一响应拦截、全局异常过滤**；日志层有 `TraceId 中间件 + Winston 结构化日志 + AI 调用耗时日志`。监控层用 `Prometheus`：HTTP 请求量/耗时、错误数、AI 调用指标，并做了路由归一化避免高基数标签，线上排障和性能分析比较直接。

### 项目流程

1. 用户先完成登录拿 JWT，后续所有核心接口都走鉴权。
2. 如果次数不足，先走充值：创建订单 -> 支付宝/微信支付 -> 回调或主动查询 -> 订单状态从 pending -> processing -> success -> 发放权益并记交易流水。
3. 用户进入 AI 功能有两条主线。
4. 简历押题流程：
   /interview/resume/quiz/stream 发起后，先做 requestId 幂等检查，再原子扣减 resumeRemainingCount，创建 consumption_record(pending)，解析简历文本，调用 AI 两阶段生成（问题+评
   估），通过 SSE 持续推送进度，成功后落库 resume_quiz_result 并把消费记录置为 success；失败则自动退款并标记 failed。
5. 模拟面试流程：
   /interview/mock/start 先扣专项/综合次数，创建会话并持久化 sessionState，SSE 流式输出开场白；
   /interview/mock/answer 每次回答都会更新问答、流式生成下一问和参考答案，支持超时自动结束；
   用户可 pause/resume/end，恢复时从数据库会话状态重建到内存继续面试。
6. 报告流程：
   /interview/analysis/report/:resultId 统一查询。
   简历押题报告直接返回；模拟面试报告是异步生成，若还在生成就提示稍后重试。
7. 全流程会沉淀关键数据：PaymentRecord、ConsumptionRecord、AIInterviewResult、UserTransaction，便于审计和问题回放。
8. 运维上接了日志追踪和 Prometheus 指标，请求耗时、错误率、AI 调用都可观测。

### 为什么选 MongoDB？

- 业务数据形态匹配

1. AI 数据是高变、深嵌套 JSON：qaList、radarData、sessionState、metadata 这类字段结构经常迭代，用文档模型比关系型更顺手。
2. 长会话状态天然是一个聚合文档：一次面试的上下文、问答、报告状态放在同一文档里，读写路径短，恢复会话简单。
3. 高频单文档原子更新足够解决核心一致性：扣次数、状态流转、幂等处理大量依赖 findOneAndUpdate + 条件，Mongo 在这类场景很直接。
4. 支付回调/AI 输出有非结构化字段：notificationPayload、passback metadata 等字段不稳定，Mongo Mixed 类型能兼顾灵活性和落库效率。
5. 查询模式明确：主要按 userId + status + createdAt 查，配合复合索引性能可控。
6. 团队效率：NestJS + Mongoose + TypeScript 一套栈，开发节奏快，schema 演进成本低。

技术选型标准我一般按这四条：

1. 业务匹配度优先（先看数据形态和访问模式）。
2. 一致性要求可闭环（原子操作 + 状态机 + 幂等）。
3. 团队可维护（学习成本和迭代速度）。
4. 可观测与可扩展（索引、监控、故障可定位）。

## 2. 技术架构

简历：建⽴了 API 层 → 业务逻辑层 → 数据持久化层的标准三层架构，确保代码清晰可维护

- 核心思想：职责单一 + 流程可追踪

- Controller 只做 HTTP 协议适配（接参数/写响应）

- Service 编排所有业务流程（扣费/调 AI/推事件）

- Schema+Model 负责数据定义和持久化操作

- 三层通过 NestJS 的依赖注入（@InjectModel、constructor 注入 Service）解耦，每层只关心自己的职责

这样做的结果是：接口变更通常只改 API 层，规则变更只改 Service，存储策略变更只动持久层，维护成本比较可控。

## 3. 异步流处理

简历：基于 RxJS Observable 的异步流处理框架，实现了⾮阻塞式流式数据传输，⽤户⽆需等待 AI ⽣成完全完成即可看到实时进度

- Service 层创建 RxJS Subject 后立即返回给 Controller 订阅，真正的 AI 调用在后台异步执行，每生成一个 token 就通过 `subject.next()` 推送，Controller 收到后立即 `res.write()` 以 SSE 格式发给前端。

- 具体拆解为三步：

1. 立即返回，后台执行：创建 Subject 后直接 return subject，Controller 拿到 Subject 就可以 `.subscribe()` 开始监听，不阻塞 HTTP 响应。
2. 逐 token yield → 逐事件推送：AI 层用 LangChain 的 `chain.stream()` 拿到异步迭代器，每收到一个 chunk 就 yield 出去；业务层消费这个 generator，每 yield 一次就调一次 `subject.next()`，把累积内容推给订阅者。
3. SSE 实时写入：Controller 在 `subscribe.next` 回调中执行 `res.write()`，配合 `flush()` 强制刷新缓冲区，前端就能实时收到每一条事件。

## 4. 流式输出处理

简历：实现了 AI 流式输出的块级处理和智能分段解析，⽀持在 AI ⽣成过程中实时提取问题和答案，精准度 > 95%

- 协议约束 + 流式状态机

1. 先在 Prompt 层定义输出协议
   要求模型固定使用 `[STANDARD_ANSWER]` 和 `[END_INTERVIEW]` 标记，把 **“问题正文”和“参考答案”** 分段输出
2. 块级流处理
   AI 返回是流式 chunk，我在服务里逐块累积到 fullQuestion，每来一块就检查是否出现 `[STANDARD_ANSWER]`。
   - 出现前：持续作为 QUESTION 流推送。
   - 出现后：立即切分为“问题区”和“答案区”，问题先收口，答案继续流式推送。
3. 智能分段解析
   流结束后再做一次全量解析（正则 + 标记清洗）：
   - 提取 `[STANDARD_ANSWER]` 段落
   - 识别 `[END_INTERVIEW]` 判断是否结束
   - 清理控制标记，得到最终 `question / standardAnswer / shouldEnd`

4. 精准度 >95% 的来源
   统计口径是“问题与答案是否被正确分段 + 结束标记是否正确识别”。通过·协议化输出、流中实时切分、流后全量校验这三层组合，解析准确率能稳定在 95% 以上。

## 5. 会话状态管理

简历：独⽴实现了完整的会话状态管理系统，⽀持⾯试的创建、进⾏中、暂停、恢复、结束等多个⽣命周期

- 这个功能我用的是“内存态 + 持久态双轨”的会话管理方案。

- 用内存 `Map<sessionId, InterviewSession>` 做热缓存支撑实时问答
- 数据库 `sessionState` 字段做持久化快照支撑暂停/恢复
- 通过 `isActive + status` 双标志位管理生命周期，暂停时从内存卸载到数据库、恢复时从数据库装载回内存，实现了完整的创建→进行→暂停→恢复→结束的状态流转。

### 为什么会话信息要做双轨？

• 核心原因是把“实时性”和“可靠性”拆开：

1. 内存轨（Map）保证实时交互
   SSE 面试是高频读写，如果每个 chunk 都打数据库，延迟和开销会明显上升。
2. 持久化轨（Mongo sessionState）保证可恢复
   浏览器断开、服务重启、用户暂停后恢复，都要靠数据库状态找回现场。
3. 单轨都不够
   只用内存会丢会话；只用数据库会拖慢流式体验。
4. 项目里的落地方式
   start 时同时写内存和 DB，过程中关键节点同步 DB，pause 清内存但保留 DB，resume 从
   DB 回填内存，end 做最终落库并清理内存。
5. 工程收益
   用户体验稳定（不卡顿）+ 业务可追踪（不丢进度），是长会话场景最实用的折中方案。

## 6. 评估系统

简历：实现了基于 AI 的多维评估系统，包含 STAR 模型分析、技能匹配度分析、雷达图数据⽣成等，⾃动计算 STAR 四维得分（Situation、Task、Action、Result）并⽣成结构化的评估报告

- 我们要把 AI 面试从 **主观点评** 升级成 **可结构化展示和可追踪** 的评估系统，核心输出是匹配度、雷达图和改进建议。

- 核心是： 数据结构定义 + Prompt 工程 + AI 结构化输出

- 本质上是 **Prompt 工程 + 结构化输出**：
  - 通过精心设计的评估 Prompt 告诉 AI 评分维度和打分规则，
  - 用 JsonOutputParser 强制输出 JSON 格式，把用户回答 + 标准答案 + 回答长度等量化数据传入让 AI 做对比分析，

- 价值是评估结果可解释、可追踪、可视化，便于用户复盘，也便于我们后续做模型效果优化。

## 7. 文档解析

简历：实现了多格式⽂档解析能⼒（PDF、DOCX、TXT、图⽚），⽀持⾃动提取结构化信息

1. 统一的文档接入层：支持上传URL和直接文本输入。
2. 对文件链接走统一解析管线：URL 校验 -> 文件下载 -> 类型分发 -> 文本清洗 -> 质量校验。
3. 类型分发里目前落地的是：PDF（pdf-parse）、DOC/DOCX（mammoth），并限制了 10MB、下载超时、空文件、权限异常等错误场景。
4. 解析成纯文本后做文本清洗和验证，过滤脏字符并检查关键词完整性。
5. “结构化信息提取”不是正则硬拆，而是把清洗后的文本交给 AI 链路，通过 Prompt + JsonOutputParser 强约束输出 JSON（如工作年限、技能、教育、匹配度、雷达图等字段）。

# Harness 的模块构成

## 一、什么是 Harness 工程？

在 AI Agent 的语境里，**Harness 工程指围绕大模型构建执行环境、工具接口、上下文与状态管理、校验和约束机制，让模型能够稳定完成任务的工程工作。**

可以把它理解为：

> **模型负责理解、推理和提出行动；Harness 负责提供上下文、执行行动、管理状态，并控制整个运行过程。**

Harness 不是某一个固定框架，也不只是提示词或 API 封装。它是承载模型执行任务的一组工程机制，可以由应用程序、Agent 框架、存储系统和外部基础设施共同实现。

为了理解职责边界，可以简化为：

> **Agent = 模型 + Harness**

这是理解架构的简化表达，而不是统一标准。不同系统对 Harness 的范围划分不同，例如有的把用户界面和长期记忆算在其中，有的只指核心执行运行时。

## 二、Harness 工程的主要模块

下面是一种常见的工程拆分，**不是必须实现的标准清单，也不意味着要创建 11 个独立服务或类**。这里的“主要负责方”指承担功能的技术组件，而不是团队人员岗位。

| 模块 | 主要作用 | 主要负责方 | 典型实现 |
| --- | --- | --- | --- |
| **输入与事件接入** | 接收用户请求和环境事件，启动或继续任务 | 应用入口 + 事件监听系统 | 对话接口、文件监听、Webhook、定时触发 |
| **指令与上下文管理** | 决定每次调用模型时提供哪些信息 | 上下文组装程序 + 检索系统 | 系统提示词、项目规则、工具说明、历史消息、上下文裁剪与摘要 |
| **模型调用与输出解析** | 调用模型，将返回结果转换成可处理的消息和行动 | 模型适配器 + 输出解析器 | API 适配、流式处理、工具调用解析、结构化输出校验 |
| **执行循环与任务编排** | 驱动模型决策、工具执行和结果回填，管理执行顺序 | 运行时 + 编排程序 | ReAct 循环、任务依赖、并行调度、停止条件、轮数限制 |
| **工具注册与执行** | 提供模型可用的能力，并实际执行调用 | 工具注册表 + 执行器 + 外部系统 | 工具 Schema、参数校验、文件操作、Shell、数据库、MCP 接入 |
| **状态、记忆与持久化** | 保存任务进度和历史，使任务能够持续执行或恢复 | 状态管理程序 + 存储系统 | 消息记录、任务状态、数据库、检查点、长期记忆 |
| **环境与权限隔离** | 提供执行空间，约束工具可以访问和修改的资源 | 环境管理器 + 权限系统 | 工作目录、容器、沙箱、网络限制、凭证管理、人工审批 |
| **反馈、校验与评测** | 检查行动结果、最终成果和系统整体表现 | 校验程序 + 评测系统，模型可辅助 | 单元测试、类型检查、业务规则、来源核对、任务成功率评测 |
| **异常处理与资源控制** | 处理失败，避免失控循环、重复操作和超预算 | 运行时 + 预算与重试策略 | 超时、取消、重试、幂等控制、Token 与费用预算 |
| **可观测性与调试** | 记录 Agent 做了什么，定位失败和性能问题 | 日志与追踪系统 | 调用链追踪、工具输入输出记录、耗时与成本统计 |
| **交付与人工介入** | 输出可用成果，并在需要时把控制权交给用户 | 交付程序 + 交互与审批系统 | 文件交付、变更预览、审批、补充提问、暂停与恢复 |

### 几组容易混淆的职责

- **上下文管理与状态存储**：存储负责“保留什么”，上下文管理负责“这一轮让模型看到什么”。保存完整历史，不等于每次都把完整历史发送给模型。
- **模型提出调用与工具实际执行**：模型输出工具名和参数，执行器负责权限检查、参数校验和真实操作。工具调用消息本身不会修改文件或访问数据库。
- **循环编排与异常控制**：编排决定正常情况下下一步如何运行；异常控制处理超时、失败、取消和预算耗尽。二者通常由同一个运行时实现。
- **单次任务校验与系统评测**：任务校验检查当前成果是否合格；系统评测通过一组测试任务比较成功率、成本和耗时，通常离线运行，不必进入每一轮执行循环。
- **模型表达完成与任务实际结束**：模型可以提出“完成”，但程序还要结合结果、校验和停止规则决定是交付、继续还是暂停。

## 三、与 Agent 的模块构成有什么关系？

[Agent 的模块构成](./Agent的模块构成.md)描述的是**整个系统需要具备的能力**；Harness 描述的是**如何通过模型之外的工程机制，把这些能力组织并执行起来**。

| Agent 能力 | 大模型主要承担 | Harness 主要承担 |
| --- | --- | --- |
| **输入与感知** | 理解文本、图片含义 | 接收输入、解析文件、接入事件 |
| **推理与决策** | 判断下一步行动 | 提供上下文、解析输出、限制可执行行动 |
| **规划与任务管理** | 生成和调整计划 | 保存计划、管理依赖、安排执行 |
| **记忆与上下文管理** | 辅助摘要、提取信息 | 存储、检索、裁剪、组装上下文 |
| **工具与行动执行** | 选择工具、生成参数 | 校验参数、执行工具、返回结果 |
| **反馈与校验** | 解释结果、提出修正 | 运行测试、执行规则、收集反馈 |
| **流程控制与运行时** | 提出继续或完成 | 驱动循环、处理暂停、决定实际停止 |
| **安全与权限控制** | 辅助识别风险 | 强制执行权限、隔离与审批 |

**Harness 的主要职责由程序承担，但某些机制也可以调用模型辅助完成**，例如生成上下文摘要、评估回答语义或解释测试失败。

不过，模型建议不等于强制约束。权限、文件访问范围和执行预算等规则，仍需要程序落实。

## 四、ReAct 与 Harness 的关系

**ReAct 是执行模式，Harness 是承载这个模式的工程系统。**

ReAct 来自 Reasoning（推理）+ Acting（行动），核心是根据当前信息决定行动，执行后观察结果，再调整下一步。

```text
用户请求 / 环境事件
        ↓
┌────────────── Harness ──────────────┐
│ 接收任务 → 组装上下文               │
│                ↓                    │
│           调用大模型                │
│                ↓                    │
│       模型提出行动或最终答案         │
│                ↓                    │
│       解析行动 → 权限与参数检查      │
│                ↓                    │
│           执行工具                  │
│                ↓                    │
│     收集结果 → 校验 → 保存状态       │
│                ↓                    │
│        继续循环 / 暂停 / 交付        │
└─────────────────────────────────────┘

异常控制、资源预算与可观测性贯穿整个过程
```

这里的“环境事件”是系统或外部环境变化产生的通知，例如文件被修改、收到新邮件或服务异常告警。通常由监听器、Webhook 或其他外部系统发现，再由应用提供给 Agent；模型并不会自动知道这些变化。

实际执行中有两条常见分支：

- **模型提出工具调用**：检查权限与参数，执行工具，将结果回填后进入下一轮。
- **模型输出最终答案**：按任务要求校验成果，然后交付；不需要再执行工具。

Harness 不一定采用 ReAct，也可以承载固定流程、先规划后执行，或其他编排方式。实际实现也不必要求模型输出完整的内部推理文字，结构化工具调用已经可以支撑决策与行动循环。

## 五、示例：一个查询当前时间的最小 Harness

以“查询北京和伦敦的当前时间”为例，模型和程序的协作过程如下：

```text
程序接收用户目标
    ↓
程序提供消息历史与 get_current_time 工具定义
    ↓
模型选择工具并生成时区参数
    ↓
程序校验参数并查询时间
    ↓
程序把工具结果写回消息历史
    ↓
模型根据结果继续决策或生成答案
    ↓
程序输出答案并结束任务
```

在一个基于 Chat Completions 的 TypeScript 实现中，常见代码与 Harness 职责可以对应为：

| 代码或配置 | Harness 职责 |
| --- | --- |
| `messages` | 当前上下文与短期状态 |
| `client.chat.completions.create()` | 模型调用 |
| `tools` | 工具注册与说明 |
| `message.tool_calls` 的解析 | 将模型输出识别为可执行行动 |
| `executeTool()` | 参数校验与工具实际执行 |
| `for` 循环 | 执行循环与最大轮数控制 |
| `timeout`、`maxRetries` | 基础超时与模型请求重试策略 |
| `role: "tool"` 消息 | 工具执行结果回填 |
| `console.log()` | 最基本的运行日志 |
| 返回最终答案 | 成果交付与结束任务 |

这个最小实现已经具备 Harness 的核心结构，但内存中的消息历史不是持久化记忆，请求重试也不等于完整的任务恢复机制。

尤其要区分**模型请求重试**和**工具操作重试**：如果工具会发送邮件、扣款或修改外部数据，超时并不一定代表操作没有发生，不能一律直接重做。需要通过操作标识、结果查询或幂等机制避免重复执行。

## 六、最小构成与扩展能力

### 最小可用构成

从模型之外的工程部分看，一个最小的工具型 Harness 通常包含：

> **上下文与状态 + 模型调用适配 + 工具执行器 + 执行循环**

基本的参数检查、错误反馈和停止条件可以直接包含在这些组件中。涉及外部操作时，还需要与工具能力相匹配的权限边界。

### 按业务需要扩展

| 业务需求 | 需要补充的工程能力 |
| --- | --- |
| 长时间运行或中途退出后继续 | 状态持久化、检查点、恢复策略 |
| 处理大型项目或大量历史信息 | 上下文裁剪、摘要、按需检索 |
| 执行具有副作用的操作 | 权限审批、幂等控制、操作结果确认 |
| 批量任务或复杂任务依赖 | 队列、调度、并发与依赖管理 |
| 发现回归并比较不同版本 | 固定测试集、评分规则、成本与耗时评测 |
| 定位线上失败 | 结构化日志、调用链追踪、敏感信息脱敏 |
| 控制运行费用 | Token 统计、成本预算、任务级截止时间 |

这些能力应根据任务需求增加，不必为了“架构完整”在最小实现里全部引入。

## 七、Agent Harness 与评测 Harness 的区别

“Evaluation Harness（评测 Harness）”是一个更窄的概念，专门负责组织测试任务、运行被测系统、评分和汇总指标。

| 类型 | 关注点 | 典型问题 |
| --- | --- | --- |
| **Agent Harness** | 让模型在实际任务中能够行动并完成交付 | 工具如何执行？状态如何恢复？权限如何约束？ |
| **评测 Harness** | 衡量模型或 Agent 的表现 | 成功率是多少？修改后是否退步？成本和耗时如何变化？ |

评测 Harness 可以调用整个 Agent Harness 运行测试，也可以只测试模型本身。二者可以配合，但不等同。

**总结：模型决定“下一步想做什么”，Harness 管理“行动如何执行、受到什么约束、结果如何检查和交付”。**

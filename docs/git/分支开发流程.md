# Git Feature 分支开发标准流程指南

## 核心原则

> **主分支（main/master）永远保持可部署状态**。所有的开发工作必须在独立的 `feature` 分支上进行，严禁直接在主分支提交代码。

---

## 流程步骤详解

### 1. 准备阶段：同步最新代码 (Sync)

在开始新功能之前，必须确保本地代码库基于最新的主分支建立，以减少冲突。

```bash
# 切换到主分支
git checkout main

# 拉取远程最新代码
git pull origin main

```

### 2. 启动阶段：创建功能分支 (Branch)

基于最新的主分支创建一个独立分支。

- **命名建议**：`feature/功能名` 或 `feat/JIRA号-描述`。

```bash
# 创建并切换到新分支
git checkout -b feature/login-page

```

### 3. 开发阶段：提交代码 (Commit)

遵循“原子提交”原则，每个 Commit 只做一件事。

```bash
# 将修改加入暂存区
git add .

# 提交代码（建议遵循 Conventional Commits 规范）
git commit -m "feat: 完成登录页面的UI布局"

```

### 4. 同步阶段：保持分支更新 (Rebase)

开发过程中，如果主分支有了新更新，需要将其同步到你的分支，防止合并冲突。

```bash
# 获取远程更新但不合并
git fetch origin main

# 将你的提交“搬运”到最新的 main 之后（推荐用 rebase 保持历史整洁）
git rebase origin/main

```

_注：若遇到冲突，解决文件冲突后执行 `git add .` 然后 `git rebase --continue`。_

### 5. 提交阶段：推送到远程 (Push)

本地测试通过后，推送到远程仓库。

```bash
# 首次推送需建立追踪关系
git push -u origin feature/login-page

```

### 6. 评审阶段：发起合并请求 (PR / MR)

在代码托管平台（GitHub/GitLab）发起 Pull Request 或 Merge Request。

1. **Code Review**：等待同事评审。
2. **CI/CD**：等待自动化测试通过。
3. **修改**：若有反馈，在本地修改并再次 `push`，PR 会自动更新。

### 7. 完成阶段：合并与清理 (Merge & Cleanup)

PR 被批准并合并后，清理本地环境。

```bash
# 切换回主分支
git checkout main

# 拉取包含新功能的最新代码
git pull origin main

# 删除本地已合并的功能分支
git branch -d feature/login-page

```

## 最佳实践速查表

| 维度            | 建议                                                            |
| --------------- | --------------------------------------------------------------- |
| **Commit 频率** | **多提交，早提交**。避免一次性提交数千行代码。                  |
| **Commit 信息** | 描述 **Why** 和 **What**。例：`fix: 处理空数据导致的崩溃`。     |
| **冲突处理**    | **尽早解决**。建议每天同步一次 `main` 分支。                    |
| **禁止操作**    | 除非非常确定，否则不要在公共分支使用 `git push -f` (强制推送)。 |
